# 隐式记忆工作范围抽取修复设计

## 1. 背景与问题

用户在成功问答中明确陈述“我平时主要做 Java 开发。”后，隐式记忆任务正常执行，但结果为 `MODEL_EMPTY`，没有产生 `AUTO_EXTRACT` 记忆。新会话因此无法回答用户常用的编程语言。

现有 Java 白名单已经支持 `WORK_COMMON_SCOPE`，并能将 Java、开发、前端、后端等封闭词汇规范化；缺口在模型抽取提示词。提示词仅强调“稳定偏好”，没有定义 `WORK_COMMON_SCOPE` 的含义，也没有工作范围的正向示例，模型因此倾向于保守返回空候选。

## 2. 目标与边界

本次修复目标是让模型把用户直接明确表达、长期稳定的职业方向、技术栈或常用工作范围识别为 `WORK_COMMON_SCOPE` 候选，例如“我平时主要做 Java 开发。”。

本次只修改隐式抽取提示词及其契约测试，不修改：

- 数据库表、任务状态或结果码；
- 记忆写入、召回、删除和索引流程；
- 现有 Java 白名单、敏感内容过滤、原文证据校验和置信度阈值；
- 显式记忆处理逻辑。

## 3. 方案

调整 `SpringAiImplicitMemoryModelClient` 的系统提示词：

1. 将抽取对象从笼统的“稳定偏好”明确为“稳定用户特征、偏好和常用工作范围”。
2. 明确定义 `WORK_COMMON_SCOPE`：用户直接陈述的长期职业方向、常用技术栈或稳定业务范围。
3. 加入一个结构严格、可通过现有 Java 校验的正向示例：
   - 输入：`我平时主要做 Java 开发。`
   - 类别：`WORK_COMMON_SCOPE`
   - 键：`work.common_scope`
   - 内容：`用户常用工作范围是Java开发`
   - 证据：逐字使用当前用户消息。
4. 保留空候选规则和全部禁止项，避免把订单、退款、物流、临时任务等业务信息误存为用户长期记忆。

不增加模型空结果重试，也不增加确定性兜底，避免额外调用成本和新的任务结果语义。

## 4. 数据流与安全边界

修复后的数据流保持不变：

1. 成功问答登记异步抽取任务。
2. 模型依据增强后的提示词产生候选。
3. Java 校验候选类别、固定键、置信度、原文证据、长度、敏感内容和封闭词汇。
4. 通过校验的候选写入 MySQL，并登记索引 Outbox。
5. 后续召回链路按既有规则使用该记忆。

模型输出仍是不可信输入。示例只改善召回率，不绕过 Java 安全校验。

## 5. 测试与验收

自动化回归测试应验证发给模型的系统提示词同时包含：

- `WORK_COMMON_SCOPE` 的清晰定义；
- “我平时主要做 Java 开发。”正向示例；
- 原有禁止项和仅输出 JSON 的约束。

同时运行隐式记忆模型客户端、候选校验、任务 Worker 和相关记忆测试，确认既有行为没有回归。

人工验收步骤：

1. 重启 Agent Server。
2. 在一个新会话发送“我平时主要做 Java 开发。”。
3. 等待异步任务完成，确认结果为 `SAVED`，且生成一条 `AUTO_EXTRACT`、`WORK_COMMON_SCOPE` 记忆。
4. 新建另一个会话，询问“我平时主要使用什么编程语言？”。
5. 应根据跨会话记忆回答 Java，不再声称无法获取用户历史偏好。
