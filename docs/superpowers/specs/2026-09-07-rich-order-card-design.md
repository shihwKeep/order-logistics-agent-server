# 生产级订单查询卡片增强设计

## 1. 背景

当前链路已经能按订单号、外部订单号或运单号精确查询有权访问的订单，并通过 `order-list` 结构化 SSE 结果展示简化订单卡片。但现有卡片只有单一金额、少量商品摘要以及合并后的承运商和运单号，不足以让坐席完成实际核单。

本设计是 `2026-09-07-order-logistics-tools-design.md` 的增量设计。既有身份认证、订单权限、内部服务凭证、工具调用保护、SSE 发布、结果持久化和物流查询规则继续生效。

## 2. 已确认决策

1. 沿用 `search_orders` 和 `/internal/agent/orders/search`，不增加第二次详情查询。
2. `order` 负责业务查询、金额口径、收款方式翻译、权限过滤和隐私脱敏；Agent 与前端不推导业务事实。
3. 每次最多返回 5 个订单；每个订单最多返回 20 条商品，前端默认展示 3 条。
4. 收货人姓名、手机号默认脱敏；地址只展示省、市、区，不返回街道和详细地址。
5. 展示“收款方式”，不增加容易混淆的“收货方式”。
6. 每个包裹单独展示承运商、运单号和发货时间，并保留“查看物流”动作。
7. 所有金额使用整数分跨服务传输，前端只格式化为元。
8. `order-list` 继续使用 `schemaVersion=1`，以可选字段做向后兼容扩展；旧历史卡片继续可读。
9. 本次不新增数据库表，不改变长期记忆，也不把实时订单数据写成长期事实。

## 3. 目标与非目标

目标：一次有权限的订单查询即可得到坐席核单所需的订单概览、金额、收货人、商品明细和多包裹概要；电话解析允许安全降级；新旧持久化卡片都能展示；查询数量、载荷大小、日志内容和下游调用次数全部有界。

非目标：不建设完整订单详情页，不增加订单写操作，不展示完整手机号和详细地址，不实现客户查询、知识库、跨会话记忆或模型路由优化，也不让前端重新计算财务结果。

## 4. 总体链路与职责

```text
坐席输入完整业务编号
    → Agent search_orders：参数校验、调用保护、注入可信身份
    → order 内部接口：鉴权、批量查询、脱敏、组装有界 DTO
    → Agent：严格校验；完整卡片发 SSE 并持久化；最小摘要给模型
    → 桌面端：展示卡片、展开商品、触发确定性查看物流动作
```

- `order` 是订单业务事实和脱敏结果的唯一生产者。
- Agent 是跨服务契约校验、工具输出分流和会话持久化边界。
- 前端只负责展示、展开收起和发送结构化动作。
- 模型不得接收完整卡片 JSON，也不得生成或改写金额、地址和手机号。

## 5. 增强接口契约

`POST /internal/agent/orders/search` 的请求和外层响应不变。`items` 中的订单卡片扩展为：

```json
{
  "orderCode": "O123",
  "outerOrderCode": "OUT123",
  "statusCode": 80,
  "statusText": "在途",
  "orderTime": "2026-09-07 12:00:00",
  "paymentMethodCode": 194,
  "paymentMethodText": "款到发货",
  "amount": {
    "goodsTotalInFen": 6000,
    "discountInFen": 0,
    "balanceDeductionInFen": 6000,
    "freightInFen": 0,
    "receivableInFen": 0
  },
  "recipient": {
    "nameMasked": "石**",
    "phoneMasked": "138****1234",
    "regionText": "湖南省 常德市 鼎城区"
  },
  "goodsTotalCount": 6,
  "goodsLineCount": 1,
  "goodsTruncated": false,
  "goods": [
    {
      "goodsName": "商品名称",
      "skuCode": "SKU001",
      "specification": "50g/袋",
      "unitPriceInFen": 1000,
      "quantity": 6,
      "subtotalInFen": 6000,
      "gift": false
    }
  ],
  "shipmentCount": 1,
  "shipmentsTruncated": false,
  "shipments": [
    {
      "carrierName": "德邦",
      "logisticsCode": "业务运单号",
      "deliveryTime": "2026-09-07 12:10:00"
    }
  ]
}
```

### 5.1 必填、可空与上限

| 字段 | 规则 |
|---|---|
| `orderCode` | 必填非空 |
| `outerOrderCode` | 可空 |
| `statusCode` | 必填 |
| `statusText` | 可空，前端显示“状态未知” |
| `orderTime` | 可空，格式沿用当前接口 |
| `paymentMethodCode/Text` | 可空，未知时显示“未知收款方式” |
| `amount` | 可空；无有效金额记录时整体为 `null`，不能伪造成全零 |
| `recipient` | 必填对象，内部字段可空但不得包含未脱敏值 |
| `goodsTotalCount` | 必填非负数，表示购买商品总件数，沿用旧契约语义 |
| `goodsLineCount` | 必填非负数，表示商品明细行总数 |
| `goodsTruncated` | 必填，返回行少于总行数时为 `true` |
| `goods` | 必填数组，最多 20 条 |
| `shipmentCount` | 必填非负数，表示有效包裹总数 |
| `shipmentsTruncated` | 必填，返回包裹少于总数时为 `true` |
| `shipments` | 必填数组，最多 10 条 |

集合始终返回数组而不是 `null`。存在的金额必须是非负整数分，商品数量必须为正数。Agent 发现越界、负金额、计数矛盾、空集合元素或结构损坏时，应拒绝该下游响应，不能静默修正。

### 5.2 旧契约兼容

新代码以 `amount`、`recipient` 和 `shipments` 为主数据源。发布过渡期仍保留旧顶层字段 `customerDisplayName`、`payAmountInFen`、`carrierName` 和 `logisticsCodes`，由新结构映射生成。新前端缺少新结构时回退渲染旧简化卡片，已持久化结果不迁移。

本次保持 `schemaVersion=1`，因为只增加可选字段且保留旧字段。只有以后发生字段改名、类型或语义不兼容时才升级版本。删除旧字段必须另开兼容性设计。

## 6. 数据来源与口径

### 6.1 订单和收款方式

- `orders.Code` → `orderCode`。
- 最新有效 `order_extend.OuterOrderCode` → `outerOrderCode`。
- `orders.Status` 及现有状态翻译 → `statusCode/statusText`。
- `orders.OrderTime` → `orderTime`。
- 最新有效 `order_extend.PaymentMethod` 的原始安全数值 → `paymentMethodCode`。
- `PayMethodConst.getValueById` → `paymentMethodText`。保留原值可以区分共享业务编码但名称不同的收款方式。

未知收款方式不能拖垮整单。订单服务保留安全编码并返回空文本，前端显示“未知收款方式”。

### 6.2 金额

金额读取该订单最新有效的 `order_money`：

- `goodsTotalInFen`：商品总金额，对应 `TotalAmount`。
- `discountInFen`：`ManualDiscount + VipDiscount + UseCoupon + UseRebate + SubsidyAmount + RedPackageAmount`，各空值按零处理；不包含单独展示的 `UseBalance` 和 `Freight`。
- `balanceDeductionInFen`：消费预存，对应 `UseBalance`。
- `freightInFen`：运费，对应 `Freight`。
- `receivableInFen`：订单应收总金额，对应 `PayAmount`。

`discountInFen` 必须由订单服务中的独立金额组装器计算，并用金额组合测试锁定上述组成项。它表示卡片所列优惠项目的合计，不承诺与其他字段组成财务平衡等式。不得用 `商品总额 + 运费 - 消费预存 - 应收` 反推优惠，因为差额和外部渠道订单可能还有其他业务字段。

金额记录不存在时返回 `amount=null`。历史空字段如何按零处理由订单服务既有金额规则决定，Agent 和前端不填业务默认值。字段名称不得使用“实付金额”，因为当前库中没有一个对所有订单都可信的单一实付字段。

### 6.3 商品明细

从 `order_goods_detail` 读取商品行，关联 `goods` 和 `goods_sku`：

- 商品名优先商品主数据，缺失时使用订单明细历史名称，再缺失显示“商品信息缺失”。
- SKU 使用 `SkuCode`，规格使用 `GoodsModel`。
- 单价使用 `PayPrice`。
- 数量优先 `SumQuantity`，为空时用 `Quantity`。
- 小计优先 `SumAmount`，为空时用 `SubtotalAmount`。
- 赠品使用已有赠品标识；零价格不能被前端擅自判定为赠品。

每个订单最多读取 21 条，前 20 条返回，第 21 条用于判定截断。`goodsLineCount` 通过按订单分组的批量计数获得，`goodsTotalCount` 通过按订单汇总有效数量获得，不能用返回数组长度冒充任一总数。明细读取使用单条有界批量 SQL：数据库支持窗口函数时使用分组行号，否则使用最多 5 个带 `LIMIT 21` 的 `UNION ALL` 子查询；禁止为每张订单循环访问 Mapper。

### 6.4 收货人信息

- 姓名来自 `orders.Receiver`，在 `order` 内脱敏。
- `orders.ReceiverTelephoneId` 是电话引用 ID，不是电话号码。订单服务批量收集合法 ID，调用现有客户服务的脱敏电话能力。
- 地区只拼接非空的 `ProvinceName/CityName/DistrictName`。
- `StreetName`、`DetailAddress`、电话引用 ID 和原始电话不得进入响应、日志或异常信息。

姓名规则：一个汉字保留原字；两个及以上保留首字，其余用 `*`；非中文名称保留首个 Unicode 字符，其余掩码。电话只接受客户服务已经脱敏的结果；如果返回疑似完整电话，订单服务必须再次掩码。

电话服务失败只令 `phoneMasked=null` 并记录无个人信息的降级标志，不能影响姓名、地区、金额、商品和包裹。一个订单存在多个电话引用时，最多返回两个已脱敏号码，以中文顿号连接；超过部分不返回。

### 6.5 包裹概要

按订单现有发货批次和运单关系批量关联 `order_delivery_batch`、`order_delivery_waybill_code` 与 `data_carrier`。每个有效运单形成一条 `shipment`。发货时间来自运单所属批次；无法可靠关联时返回 `null`，不能用制单时间代替。包裹总数按订单批量计数，明细采用与商品相同的有界分组查询方式，每单返回前 10 个；更多时设置 `shipmentsTruncated=true`。

卡片只展示包裹概要，不携带轨迹正文。“查看物流”仍发送已有确定性 `QUERY_ORDER_LOGISTICS` 动作并实时查询。

## 7. 后端查询、降级与一致性

查询顺序：

1. 规范化编号并建立不可省略的订单访问范围。
2. 在 SQL 中带权限条件执行精确查询，最多取得 5 个订单。
3. 收集已授权订单 ID，仅在 `order` 内部使用。
4. 批量读取扩展信息、金额、商品计数、前 21 条商品和包裹概要。
5. 批量解析电话引用并做二次脱敏校验。
6. 组装白名单响应，执行数量、金额与隐私校验。

| 失败点 | 处理 |
|---|---|
| 权限服务 | 失败关闭，整次查询拒绝 |
| 基础订单查询 | 整次查询失败 |
| 没有有效金额记录 | 对应订单 `amount=null` |
| 电话解析 | 对应订单 `phoneMasked=null` |
| 没有商品记录 | 对应订单 `goods=[]`、`goodsLineCount=0` |
| 没有包裹记录 | 对应订单 `shipments=[]`，允许稍后查看物流 |
| 收款方式未知 | 保留安全编码，文本为空 |

只有外部电话解析失败允许局部降级。权限、基础订单、金额、商品或包裹数据库查询发生超时或异常时，整次查询失败，不能伪装成真实空数据。历史记录本身缺失按上表表达。负金额、数量越界、内部主键外泄等契约或安全问题同样必须失败。

这是只读查询快照，不使用跨表长事务阻塞业务写入。`queriedAt` 表示组装完成时刻。持久化的是当时的卡片快照；读取历史时不得重新查询订单库并静默改写旧结果。

## 8. Agent 侧处理

Agent 扩展订单、商品、金额、收货人和包裹领域记录及 Feign 解码模型，并校验：订单最多 5 条，商品最多 20 条，包裹最多 10 条；`goodsLineCount >= goods.size()`、`shipmentCount >= shipments.size()`；对应截断标志为 `false` 时总数必须等于数组长度；金额非负；数量有效；集合无空元素；不包含内部订单 ID、电话引用 ID、完整电话或详细地址。

完整卡片仍通过 `ToolOutputPublisher` 发布 `order-list/v1` 并在收尾事务中持久化。`OrderQueryTools.toSearchModelText` 只给模型查询时间、匹配数、订单号、状态、商品总数和截断标志。收货人、电话、地区、金额拆分和完整商品列表不进入模型提示词。

SSE 顺序、同参去重、单轮工具上限、结果持久化和历史损坏降级规则保持不变。

## 9. 前端展示

一张卡片按顺序包含：

1. 订单概览：订单号、状态、外部订单号、制单时间、收款方式。
2. 金额信息：商品合计、优惠抵扣、消费预存、运费、应收金额。
3. 收货信息：脱敏姓名、脱敏电话、省市区。
4. 商品明细：商品名、SKU、规格、单价、数量、小计、赠品标签。
5. 发货包裹：每个包裹独立显示承运商、运单号和发货时间。

商品默认展示 3 条，超过后显示“展开全部（N）”，展开最多 20 条。`goodsTruncated=true` 时提示“仅展示前 20 条，还有更多商品，请前往订单详情查看”。`shipmentsTruncated=true` 时提示“仅展示前 10 个包裹”，并允许用户通过查看物流获取当前订单的有界实时物流结果。

多个订单时第一张默认展开，其余折叠；每张卡片有独立状态和自己的查看物流动作。多订单不能继续使用数组第一项作为按钮订单号。

`amount=null` 显示“金额信息暂不可用”；合法零金额显示 `¥0.00`。前端只格式化分为元，不计算总和或验证财务等式。

有新结构时渲染增强卡片；只有旧字段时渲染当前简化卡片；单条损坏历史结果降级为普通消息，不影响整个会话加载。

## 10. 安全与可观测性

- 权限过滤发生在订单 SQL 内，不能先查再内存过滤。
- Agent 和前端不接收订单内部主键、客户 ID、电话引用 ID、街道或详细地址。
- 日志不记录姓名、电话、地区全文、完整订单号、完整运单号或卡片 JSON。
- 前端只以文本节点渲染下游字符串，不使用 `v-html`。
- 不存在和无权访问保持相同外部语义。
- 联调期间已暴露的内部服务 Token 必须在上线或共享环境部署前轮换。

结构化日志或指标记录 `requestId`、访问模式、订单数、商品行数、包裹数、商品截断订单数、各附属查询降级标志、总耗时和结果状态。订单号、运单号、用户和电话不能作为指标标签。

## 11. 测试设计

### 11.1 `order`

- 三种编号查询继续强制 SQL 权限。
- 最新有效扩展记录提供外部订单号和收款方式。
- 已知、聚合和未知收款方式翻译。
- 金额存在、缺失、零值、历史空字段和负数脏数据。
- 商品单价、数量、小计、规格、赠品以及 3/20/21 条截断。
- 多订单批量查询，断言不存在 N+1。
- 中文/非中文姓名掩码，电话二次掩码与超时降级。
- 省市区缺项拼接且永不包含街道、详细地址。
- 单包裹、多包裹、无包裹、无承运商、无发货时间和超过 10 个包裹的总数与截断标记。
- 电话服务失败仍返回其余订单数据；金额、商品和包裹数据库查询失败则整次失败。

### 11.2 Agent

- 增强字段解码及旧字段兼容。
- 负金额、非法数量、计数矛盾、数组越界和空元素被拒绝。
- 完整卡片走 SSE 和持久化，模型只收到最小摘要。
- 新旧 `order-list/v1` 均可历史恢复。

### 11.3 桌面端

- 分转元、零值与缺失值区分。
- 商品默认 3 条、展开到 20 条及更多提示。
- 多订单折叠状态隔离，多包裹正确展示。
- 每张卡片查看物流动作携带正确订单号。
- 新 `v1`、旧 `v1` 和损坏载荷的恢复路径。
- 长文本、小窗口、滚动区域和 HTML 注入防护。

### 11.4 端到端验收

用已确认的测试订单验证状态、制单时间、款到发货、金额构成、商品明细、脱敏收货信息、包裹发货时间、查看物流以及刷新后的历史恢复。自动化断言不得写死真实个人信息或完整运单号。

## 12. 发布与回滚

1. 先发布 `order`，同时提供旧字段与增强字段。
2. 直接验证权限、隐私、金额口径、商品上限和多包裹数据。
3. 发布 Agent，使其校验并持久化增强结构且兼容旧响应。
4. 发布桌面端，优先渲染增强结构并保留旧结果回退。
5. 完成端到端验证，观察降级率、契约错误和查询延迟后扩大范围。

回滚时可先回滚前端或 Agent；`order` 保留旧字段即可继续服务旧消费者。不得先删除旧字段。

## 13. 验收标准

- 一张卡片可完成订单概览、金额、收货人、商品和发货包裹的基本核对。
- 消费预存不被误写为现金实付，应收零元不被误判为数据缺失。
- 商品默认简洁、可展开且服务端有界。
- 多包裹不再合并成模糊字符串。
- 电话服务故障不拖垮订单卡，但完整电话和详细地址绝不外泄。
- 旧会话简化卡片继续显示。
- 模型不重复卡片正文。
- 关键 Mapper、组装、网关校验和前端交互均有自动化测试。
- 不新增数据库迁移，不缓存实时订单状态或金额，不扩大当前范围。
