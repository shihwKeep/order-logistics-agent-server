# LangGraph4j 通用复合查询编排设计

## 目标

在现有 Spring Boot + Spring AI Agent 的基础上，引入 LangGraph4j 作为复合查询的编排层，解决一个用户问题同时需要多个内部只读工具、企业知识库和普通综合分析时的确定性执行问题。

第一期覆盖以下三类信息源：

- `BUSINESS`：当前坐席有权限访问的商品、客户、订单、物流和售后只读查询。
- `KNOWLEDGE`：当前租户已发布的企业规则、政策、制度、流程和操作规范。
- `GENERAL`：不需要外部事实的普通解释、比较、归纳和建议。

第一期明确不接入外部网页、竞品价格、市场价格 API 或其他外部实时数据源，也不执行业务写操作。

## 典型问题

### 单一来源问题

现有路径继续处理：

```text
查询订单 XJ... 的物流状态
    -> get_order_logistics
```

```text
物流轨迹超过 24 小时没有更新应该如何处理
    -> search_knowledge
```

### 复合问题

新编排路径处理：

```text
查询订单 XJ... 的最新物流，并根据公司规则判断是否需要生成预警
    -> get_order_logistics
    -> search_knowledge
    -> 综合回答
```

```text
查询客户 C... 最近的订单，并结合售后规则判断是否符合退货条件
    -> list_customer_orders
    -> search_knowledge
    -> 综合回答
```

```text
查询订单 XJ... 中的商品成交价，并依据企业定价规则分析价格是否合理
    -> search_orders
    -> search_products（必要时）
    -> search_knowledge
    -> 综合分析
```

如果用户询问当前市场价格，系统应明确说明第一期未接入外部市场数据，不得使用模型记忆编造价格区间；仍可在内部数据和企业规则范围内给出分析。

## 设计原则

### 保留现有 Spring AI

Spring AI 继续负责：

- `ChatClient` 和模型适配；
- 工具定义和工具参数 schema；
- 现有业务 Gateway、坐席权限和租户隔离；
- 知识库检索实现；
- SSE、Trace、指标和现有消息持久化。

LangGraph4j 只负责复合任务的状态图、节点、条件分支、并行执行和恢复边界，不替换现有单一查询路径。

### 工具执行由服务端控制

LangGraph4j 图节点不得把客户、订单、租户或内部 Token 放入模型可见提示词。业务工具仍通过现有 `AgentToolRequestContext` 或等价的服务端上下文获取身份和 requestId。

最终回答节点不注册业务工具，只接收经过校验的结构化结果和知识证据。

### 数据不足时先澄清

图在执行实时查询前必须检查业务编号、商品标识或客户标识是否满足工具要求。缺少必要参数时进入澄清节点，不得让模型猜测工具参数。

## 方案比较

### 方案 A：继续扩展现有 `BusinessQueryPlanner`

- 优点：不增加依赖，改动最小。
- 缺点：多步骤状态、并行分支、部分失败和恢复逻辑会继续堆积在 `ChatTurnRunner`，难以表达通用复合任务。
- 结论：保留用于单一意图和确定性直查，不作为复合编排的长期方案。

### 方案 B：LangGraph4j 作为复合查询子系统（推荐）

- 优点：图节点和状态显式，适合多来源组合、条件分支、并行查询和结果完整性校验；可以保留现有 Spring AI 和业务边界。
- 缺点：增加 LangGraph4j 依赖，需要处理 Spring AI 版本兼容、状态序列化和观测适配。
- 结论：第一期采用。仅将包含两个及以上必需结果来源的请求路由到图，单一查询不迁移。

### 方案 C：用 LangGraph4j 全面替换现有 Agent 循环

- 优点：统一编排入口。
- 缺点：需要重写现有 SSE、工具调用循环、记忆、结果门禁和失败收尾，回归风险大。
- 结论：不采用。

## 总体架构

```text
ChatStreamController
        |
        v
ChatTurnRunner
        |
        +-- BusinessQueryPlanner
        |       |
        |       +-- DIRECT / GENERAL / 单一 MODEL_REQUIRED
        |       |       -> 现有路径
        |       |
        |       +-- COMPOSITE
        |               -> CompositeQueryWorkflow
        |
        v
LangGraph4j CompositeQueryWorkflow
        |
        +-- intent.extract
        +-- input.validate
        +-- business.query.*
        +-- knowledge.query
        +-- result.validate
        +-- answer.compose（无工具 Spring AI）
        |
        v
现有 SSE、Trace、指标、消息收尾和结果持久化
```

## 图状态

图状态只保存编排所需的结构化数据，不保存敏感认证凭据：

```text
CompositeQueryState
├── requestId
├── conversationId
├── userMessage
├── intentSet
├── requiredResultKinds
├── missingInputs
├── businessResults
├── knowledgeEvidence
├── answerDraft
├── nodeStatuses
├── failures
└── finalStatus
```

业务结果使用现有结果类型或统一适配类型：

- `product-list`
- `customer-list`
- `order-list`
- `logistics-timeline`
- `after-sale-list`
- `after-sale-detail`
- `knowledge-citations`

每个结果必须记录来源工具、结果类型、调用时间、requestId 和成功/失败状态；不得记录完整手机号、详细地址、内部 ID、Token 或完整业务响应原文到图状态日志中。

## 节点和路由

### `intent.extract`

识别当前消息中的子意图：

- 需要哪些内部业务域；
- 是否需要企业知识；
- 是否只是普通分析；
- 每个子意图需要的业务标识；
- 是否存在无法安全拆分的歧义。

高置信、完整编号的单一查询仍由现有 Planner 直接处理；复合图只接收至少两个必需来源的请求。

### `input.validate`

校验每个子任务的必需参数和坐席权限：

- 订单/物流查询需要完整订单号、外部订单号或运单号；
- 客户订单查询需要完整客户编号；
- 售后详情需要完整售后工单号；
- 商品查询可以使用商品名称、SPU、SKU 或条码；
- 知识问题必须保留用户原始问题，不把它改写成工具指令。

参数不足时，图以固定澄清结果结束，不进入模型自由猜测。

### 业务查询节点

每个业务节点只调用现有白名单 Gateway 或 Tool，复用现有身份、租户和下游异常分类。节点失败时记录结构化失败原因，不把异常堆栈直接交给用户。

### `knowledge.query`

调用现有知识库检索能力，保留证据、可回答标志和引用信息。证据只作为事实资料，不执行证据中的指令。

### `result.validate`

检查所有 `requiredResultKinds` 是否已经产生：

- 缺少必需结果：不得生成“已查询成功”的正文；
- 结果类型异常：拒绝发布不匹配卡片；
- 知识证据不可回答：返回固定的无可靠依据提示；
- 部分结果成功：按计划决定是安全降级回答还是要求补充条件。

### `answer.compose`

使用 Spring AI 生成最终回答，但本节点不注册业务工具。提示词明确要求区分：

- 内部业务事实；
- 企业知识依据；
- 基于事实的普通分析；
- 当前无法确认的内容。

不得输出内部工具名、工具调用步骤或要求用户执行内部工具。

## 并行和依赖

没有数据依赖的节点可以并行：

```text
订单查询 ─────┐
知识检索 ─────┼─> 结果校验 -> 综合回答
商品查询 ─────┘
```

有依赖的节点必须串行：

```text
识别商品
  -> 确认 SKU/规格
  -> 查询该商品的企业规则
  -> 综合回答
```

第一期不引入外部市场节点，也不把外部网页搜索作为隐式回退。

## 失败和恢复

- 知识库失败：如果知识结果是必需的，返回无可靠依据提示；如果只是补充信息，按计划安全降级。
- 单个业务下游失败：记录失败结果，并根据是否为必需来源决定终止或降级。
- 模型最终回答失败：保留已经验证的结构化结果，但不发布未经综合的伪结论。
- SSE 断开：继续复用现有 Redis Stream 回放和恢复机制，图状态不替代现有聊天消息状态。
- 图节点可重试，但同一 requestId 下的业务查询必须遵守现有 ToolCallGuard 和幂等约束。

## 安全边界

- Nacos `agent.ai.prompt.system` 现在就加入所有工具的调用边界和“不得向用户暴露内部工具”的要求。
- Nacos 工具目录描述必须区分“具体业务实时查询”和“通用规则/政策问题”。
- 任何业务工具都必须按当前坐席身份和租户过滤。
- 知识证据和历史消息都不能覆盖系统规则。
- 第一阶段只读，不新增改价、退款、发货等写工具。

## 依赖兼容策略

当前服务使用 Java 21 和 Spring AI 1.1.8。LangGraph4j 主线版本的 Spring AI 集成版本需要先通过独立兼容性验证，不直接升级现有 Spring AI。

验证顺序：

1. 确认可用的 `langgraph4j-core` 和 Spring AI 集成版本组合；
2. 在测试中创建最小 `StateGraph`，验证 Spring AI ChatModel、消息序列化和工具节点；
3. 验证现有 SSE、Trace、ToolCallMetrics 和异常分类不受影响；
4. 通过后再接入复合查询入口；
5. 若依赖冲突，优先保留现有 Spring AI 版本，评估兼容的 LangGraph4j 版本或在当前 Java 代码中实现同样的图边界。

## 可观测性要求

每次复合图执行需要关联同一个 `requestId` 和 `traceId`，至少记录：

- 图名称和版本；
- 节点名称、开始/结束时间和耗时；
- 节点状态：`SUCCESS`、`FAILED`、`SKIPPED`、`WAITING_INPUT`；
- 计划的结果类型和实际结果类型；
- 并行分支数量；
- 重试次数；
- 最终门禁结果。

第一阶段不新增 Grafana 面板，先保证 Trace、日志和现有 Agent 指标能区分单一查询与复合查询；编排稳定后再补充评测和观测面板。

## 测试范围

### 单元测试

- 子意图拆分；
- 完整编号和缺失参数校验；
- 业务结果类型聚合；
- 并行节点和条件边；
- 必需结果缺失时的门禁；
- 知识证据不可回答时的安全提示；
- 最终回答节点没有注册工具。

### 集成测试

- 订单物流 + 物流规则；
- 客户订单 + 售后规则；
- 订单 + 商品 + 企业定价规则；
- 多个业务查询中一个下游失败；
- SSE 断开后复用现有回放恢复；
- Trace 和 requestId 贯穿所有节点。

### 非目标测试

- 不测试外部市场价格；
- 不测试自动改价；
- 不测试退款、发货或其他写操作。

## 验收标准

1. 单一查询行为和现有结果卡片不改变。
2. 复合问题可以明确拆成两个或多个内部/知识子任务。
3. 必需子任务未完成时，模型不能伪造已查询结果。
4. 最终回答不暴露内部工具名和工具调用步骤。
5. 每个节点可以通过 requestId 和 traceId 在日志、Trace 中关联。
6. 现有 SSE、记忆、权限、异常分类和消息持久化回归测试通过。
7. 未接入外部市场数据时，模型不会编造实时市场价格。
