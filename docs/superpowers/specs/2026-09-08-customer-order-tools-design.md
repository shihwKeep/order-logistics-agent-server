# 客户与客户订单查询工具生产设计

## 1. 背景与目标

当前 Agent 已经具备商品查询、订单精确查询和物流查询能力，但还不能先定位客户，再查询该客户的订单。现有业务代码中已经存在客户主数据接口和客户订单列表逻辑，不过旧接口的身份、权限和返回字段边界不满足 Agent 直接调用要求。

本阶段建设两项只读工具：

1. `search_customers`：按客户编号或客户姓名精确查询当前坐席有权访问的客户。
2. `list_customer_orders`：通过客户编号重新解析可信客户身份，并查询当前坐席订单权限内的近期订单。

目标是打通“用户描述客户 → 展示客户卡片 → 确定唯一客户 → 展示现有丰富订单卡片”的生产链路，同时保证模型、前端和调用方都不能通过自报 `customerId` 绕过客户权限或订单权限。

## 2. 范围

### 2.1 本阶段包含

- 客户编号精确查询。
- 客户姓名精确查询，重名时返回客户列表，不自动选择。
- 客户列表结构化 SSE 结果和桌面端客户卡片。
- 客户卡片“查看订单”确定性动作。
- 使用可信客户身份查询最近订单。
- 复用现有 `order-list` 丰富订单卡片。
- 客户结果持久化、历史恢复和上下文安全压缩。
- 客户服务与订单服务的双重权限检查。
- 功能开关、组织灰度、超时、有限重试、熔断和可观测日志。

### 2.2 本阶段不包含

- 手机号查询或手机号解密。
- 客户模糊搜索、拼音搜索和全文检索。
- 客户信息新增、修改、合并、转移或重新分配。
- 客户余额、完整电话、详细地址、身份证、生日和内部备注展示。
- 订单新增、修改、取消、退款或其他写操作。
- 客户跨会话长期记忆。
- 知识库 RAG、售后查询和客服工单查询。
- 通用意图识别和多工具编排优化。

## 3. 现状结论

### 3.1 客户查询

`customerservice` 已存在 `POST /customerservice/customer/getMyCustomers`，支持通过 `codeOrName` 查询客户。然而控制器虽然要求 `loginId`，服务实现实际调用 `CustomerMapper.selALLCus`，SQL 没有使用登录人或客户归属范围。因此不能把该接口直接暴露给 Agent。

客户主数据还提供按 ID、客户编号、客户列表和默认地址查询等接口。它们可以作为 `customerservice` 内部适配的数据来源，但不能由 Agent 直接调用并自行承担客户权限和敏感字段过滤。

### 3.2 客户订单查询

`order` 已存在：

- `POST /order/list`，查询对象支持 `customerId`。
- `POST /order/customer`，专门查询客户订单。

旧的 `selectCustomerOrder` 流程会把 `isGlobal=1` 和 `isSelf=0` 写入查询条件，因此不能直接作为 Agent 的权限边界。Agent 应复用当前专用订单查询模块的身份认证、`AgentOrderAccessScope`、SQL 内强制权限过滤和丰富订单卡片聚合，只新增按可信 `customerId` 查询的入口。

## 4. 架构选择

采用领域服务分别负责自身数据的方案：

```text
桌面端
  → Agent
      → customerservice Agent 内部接口
          → 内部身份校验
          → 客户数据权限解析
          → 客户精确查询与字段白名单
      → order Agent 内部接口
          → 内部身份校验
          → 订单数据权限解析
          → CustomerId + 订单权限 SQL 过滤
          → 现有订单卡片聚合
```

不采用以下方案：

- 不把客户查询放入 `order`。这会让订单服务承担客户权限、客户脱敏和客户查询契约。
- 不让 Agent 直接调用客户主数据服务。否则身份、权限、敏感字段治理和下游故障处理会堆积在 Agent。
- 不复用旧 `/order/customer` 作为 Agent 查询入口。它的权限语义不满足失败关闭要求。

## 5. 客户服务内部接口

### 5.1 路径与认证

`customerservice` 新增：

```http
POST /internal/agent/customers/search
```

接口只在功能开关开启时注册。它复用订单链路采用的可信内部请求头语义：

- `X-Agent-Internal-Token`
- `X-Agent-Tenant-Id`
- `X-Agent-User-Id`
- `X-Agent-Org-Id`
- `X-Agent-Request-Id`

控制器不接收请求体中的租户、坐席或组织身份。内部 Token 缺失或不一致返回认证失败，可信身份字段缺失或非法返回参数失败。

### 5.2 请求

```json
{
  "keyword": "C12345",
  "matchType": "AUTO"
}
```

`matchType` 只允许：

- `AUTO`
- `CUSTOMER_CODE`
- `CUSTOMER_NAME`

`keyword` 去除首尾空白后不能为空，长度上限为 64 个字符，禁止 ISO 控制字符。

`AUTO` 按客户编号精确查询；未命中时再按客户姓名精确查询。任何模式都不执行 `%keyword%` 模糊匹配。

### 5.3 权限

客户权限由 `customerservice` 解析，不相信 Agent 请求体携带的范围。权限模型至少表达：

- `GLOBAL`：允许访问全部有效客户。
- `ASSIGNED_USER_SET`：只允许访问归属于权限用户集合的有效客户。
- `SELF`：只允许访问当前坐席名下的有效客户。

范围查询必须在 SQL 中与客户条件同时执行。非全局范围通过有效 `cus_belong` 关系约束 `CurrentUserId`，不能先查询客户再在 Java 内存中过滤。

权限服务返回空、格式异常、超时或不可用时失败关闭。只有权限系统明确返回全局权限时才能使用 `GLOBAL`。空集合不等于全局权限。

### 5.4 响应

内部响应最多取 11 条，其中第 11 条只用于判断截断；对 Agent 最多返回 10 条。

```json
{
  "matchedBy": "CUSTOMER_NAME",
  "total": 2,
  "truncated": false,
  "queriedAt": "2026-09-08T12:00:00+08:00",
  "items": [
    {
      "customerId": 123,
      "customerCode": "C12345",
      "displayName": "张*",
      "gradeName": "普通会员",
      "assetTypeName": "A类",
      "customerTypeName": "普通客户"
    }
  ]
}
```

`customerId` 只用于 Agent 服务间编排和结构化结果，不写入模型可见的自然语言摘要。客户姓名在服务端脱敏。接口不返回身份证、生日、电话、地址、余额、备注或客户主数据原始对象。

## 6. 订单服务内部接口

### 6.1 路径

`order` 在现有 Agent 内部控制器中新增：

```http
POST /internal/agent/orders/by-customer
```

请求体只包含已由 Agent 从客户服务响应取得的 `customerId`。当前阶段返回该客户最近 5 张当前坐席有权访问的有效订单。

### 6.2 强制权限

查询 SQL 必须同时包含：

```text
orders.CustomerId = :customerId
AND orders.IsDeleted = 0
AND 当前 AgentOrderAccessScope 对应的 GLOBAL / ORG_SCOPE / SELF 条件
```

权限范围沿用现有 `AgentOrderAccessService`，禁止调用旧 `selectCustomerOrder` 中写死全局权限的路径。未查询到数据时不区分客户没有订单与坐席无权访问该客户订单。

### 6.3 聚合与响应

按 `orders.Id DESC` 返回最近订单。订单基础信息、金额、商品统计、最多 20 行商品、包裹统计、最多 10 个包裹和脱敏收货人继续复用 `AgentOrderQueryService` 已有的批量聚合与 `AgentOrderCardAssembler`，不复制另一套订单卡片装配逻辑。

响应继续使用现有 `AgentOrderSearchResponse` 和 `order-list` schemaVersion `1`。匹配来源增加 `CUSTOMER`，或以独立的查询来源字段表达按客户查询，不能伪装成订单编号命中。

## 7. Agent 工具与调用链

### 7.1 `search_customers`

工具参数：

- `keyword`
- 可选 `matchType`

Agent 通过独立 Feign 客户端调用 `customerservice`。工具完整结构化结果通过 SSE 发布并写入消息结果表；返回给模型的紧凑文本只包含结果数量、客户编号、脱敏姓名、等级和类型。

客户重名时模型必须要求用户确认，不得自行选择第一条。

### 7.2 `list_customer_orders`

工具参数使用客户编号，不向模型暴露数值型 `customerId`：

- `customerCode`

调用顺序固定为：

1. Agent 使用客户编号调用客户服务精确查询。
2. 客户服务重新执行当前坐席客户权限检查。
3. 必须得到唯一客户，否则停止。
4. Agent 从内部响应取得可信 `customerId`。
5. Agent 调用订单服务按客户查询。
6. 订单服务重新执行当前坐席订单权限检查。
7. Agent 发布现有 `order-list` 结构化结果。

因此，模型不能通过生成任意 `customerId` 直接访问客户订单。

### 7.3 客户卡片动作

`customer-list` 客户卡片提供“查看订单”按钮。按钮只提交客户编号，进入 `ChatActionDispatcher` 的确定性动作分支，不经过模型重新选择工具。

客户编号不是授权凭据。即使按钮参数被修改，Agent 仍必须按 `list_customer_orders` 的完整链路重新解析客户，并由客户服务检查客户权限、订单服务检查订单权限；任何一层失败都不返回数据。因此不需要为了按钮动作新增可伪造的前端权限状态，也不需要改造现有消息结果主键契约。

## 8. 结构化结果与前端

新增结果类型：

```text
kind = customer-list
schemaVersion = 1
```

客户卡片展示：

- 脱敏客户姓名
- 客户编号
- 客户等级
- 客资类型
- 客户类型
- “查看订单”按钮

不展示空标签，不在前端执行脱敏，不在前端推导权限。客户查询为空时展示明确的空状态；客户重名时保持多卡片列表，由用户选择。

`AgentMessageQueryService` 增加 `customer-list` schemaVersion `1` 白名单，使桌面端重新进入会话后能够恢复客户卡片。客户结果与终态助手消息继续在同一数据库事务内提交。

## 9. 模型上下文与记忆边界

系统提示词增加以下业务边界：

- 查询客户实时信息时必须调用客户工具。
- 查询客户订单时必须调用客户订单工具。
- 重名客户不得自动选择。
- 客户卡片和订单卡片已经展示完整结构化数据，模型只作简短概括。
- 历史消息和会话摘要中的客户信息不能替代实时查询。

客户工具 schema 和紧凑结果必须纳入现有 Token 预算。客户实时结果不得进入会话长期摘要中的稳定事实，也不写入跨会话记忆。

## 10. 故障、重试与可观测性

Agent 到客户服务和订单服务分别设置连接超时、读取超时、熔断和并发隔离。

- 连接失败、读取超时和 HTTP 502/503/504 最多显式重试一次。
- 400、401、403、404、业务参数错误和权限拒绝不重试。
- 客户查询失败时不继续调用订单服务。
- 客户成功但订单为空返回正常空列表。
- 工具关闭时不向模型注册相应 ToolCallback。

日志只记录 `requestId`、工具名、匹配类型、结果数量、截断标记、耗时、状态和安全错误码。日志不记录搜索关键词、客户编号、客户姓名、客户 ID、内部 Token 或下游响应正文。

## 11. Nacos 配置边界

所有业务配置只进入 Nacos，不写入 `application.properties` 或其他仓库内配置文件。配置至少包括：

- `customerservice` Agent 内部接口开关、内部 Token、查询上限。
- Agent 客户服务地址、客户工具开关、灰度模式和组织白名单。
- Agent 客户订单工具开关、灰度模式和组织白名单。
- 客户服务与订单服务的连接超时、读取超时、熔断和并发隔离参数。
- 客户结果最大字节数和模型工具预算预留。

真实内部 Token 只通过进程环境变量注入 Nacos 占位符，不提交到 Git。空白、未知灰度模式按关闭处理。功能开关开启但地址、Token 或必需上限缺失时应用启动失败并指出具体配置项。

## 12. 测试与验收

### 12.1 客户服务

- 客户编号精确命中。
- 客户姓名精确命中和重名结果。
- `AUTO` 先编号后姓名。
- 空白、超长、控制字符和未知匹配类型。
- 全局、权限用户集合、本人和空权限。
- 权限服务超时、异常响应和空响应全部失败关闭。
- SQL 中同时存在客户条件和权限条件。
- 最多 10 条结果及截断标识。
- 返回 DTO 不包含禁止字段。
- 内部 Token 和可信身份头校验。

### 12.2 订单服务

- 按客户查询最近订单。
- `CustomerId` 与 GLOBAL、ORG_SCOPE、SELF 条件同时生效。
- 无订单和越权订单都不泄露订单存在性。
- 复用现有金额、商品、包裹和收货人聚合。
- 商品或包裹超限时正确截断并保留总数。
- 内部接口关闭时控制器不注册。

### 12.3 Agent

- 客户工具参数校验、紧凑模型结果和结构化结果发布。
- 客户编号重新解析为唯一可信客户后才调用订单服务。
- 客户查询失败或多结果时不调用订单服务。
- 客户结果、订单结果、助手消息的持久化边界。
- 客户工具和客户订单工具独立灰度。
- 下游超时、有限重试、熔断和错误映射。
- 单轮工具调用上限继续生效。

### 12.4 前端与端到端

- `customer-list` 卡片、空状态和重名列表。
- 修改“查看订单”动作中的客户编号不能绕过客户权限或订单权限。
- 历史恢复后客户卡片仍可展示和重新发起授权查询。
- 完整事件顺序保持 `session/status/result/delta/done`。
- 客户卡片进入订单卡片后，订单的物流按钮继续可用。
- 日志、模型上下文、SSE 和历史接口不泄露禁止字段。

## 13. 发布顺序

1. 在 `customerservice` 发布关闭状态的内部客户接口。
2. 验证内部认证、客户权限、SQL 执行计划和脱敏契约。
3. 在 `order` 发布关闭状态的按客户 Agent 内部接口。
4. 验证订单权限和丰富订单聚合。
5. 在 Agent 发布关闭状态的两个工具、结果持久化和确定性动作。
6. 发布桌面端客户卡片。
7. 仅对测试组织开启客户查询，观察错误率、延迟和无结果率。
8. 开启客户订单查询，验证客户卡片到订单卡片再到物流卡片的链路。
9. 稳定后扩大灰度范围，并保留各层独立关闭能力。

## 14. 后续衔接

完成本阶段后，依次建设售后只读查询、客服工单查询、ES + Milvus 知识库 RAG 和跨会话客户记忆。所有业务工具稳定后，再统一学习和完善意图识别、工具选择、冲突处理及多工具编排。
