# 实时业务查询强制新鲜结果设计

## 1. 背景与问题

坐席连续查询同一售后工单 `HH20260414_00002` 时，第二轮助手返回了“详情卡片已展示”，但该轮没有产生卡片。数据库证据显示：

- 13:41:38 的 USER 与 ASSISTANT 消息均成功落库；
- 对应 ASSISTANT 消息没有 `agent_message_result`；
- 最近一条 `after-sale-detail` 仍是 13:09:20 的旧结果；
- 旧结果的真实 JSON 能通过桌面端 `parseChatResult` 校验；
- 当前桌面包中也包含 `after-sale-detail` 解析与详情卡片组件。

因此根因不是前端布局、结构化结果协议或 SSE JSON 格式，而是模型参考历史回答后跳过了本轮工具调用，并生成了虚假的查询成功文案。实时业务数据不能由历史消息、短期记忆或长期摘要代替当前查询。

## 2. 目标

为商品、订单、物流、客户、客户订单、售后列表和售后详情建立统一的新鲜结果约束：

1. 参数完整且能够高置信识别的请求走确定性查询，不由模型决定是否调用工具。
2. 仍需模型理解的实时业务请求必须在本轮产生匹配的 `ToolUiResult`，才能展示查询正文和卡片。
3. 历史消息、历史卡片和会话摘要均不能满足本轮的新鲜结果要求。
4. 模型没有调用工具、调用错误工具或下游失败时，不允许发送和保存“已查询”“卡片已展示”等成功语义。
5. 普通问答保持当前流式体验；已有权限、灰度、熔断、脱敏、结果有界化和事务收尾能力继续复用。

## 3. 非目标

- 本阶段不建设完整的通用意图识别平台。
- 本阶段不自动编排一句话中的多个独立业务查询。
- 不把实时业务结果写入会话摘要或跨会话记忆。
- 不修改现有业务卡片字段和视觉设计。
- 不复制商品、订单、客户或售后的 Gateway 查询实现。
- 不依靠新增提示词作为唯一正确性保障。

## 4. 总体架构

每轮请求在读取历史和调用模型之前先进入 `BusinessQueryPlanner`：

```text
用户请求
   │
   ▼
BusinessQueryPlanner
   ├─ GENERAL
   │    └─ 当前普通问答流式链路
   │
   ├─ DIRECT
   │    └─ DirectBusinessQueryExecutor
   │         └─ 既有应用服务/Gateway
   │              └─ ToolUiResult → SSE result → 固定正文 → 统一收尾
   │
   └─ MODEL_REQUIRED
        └─ 当前模型与工具调用链
             ├─ ToolUiResult 暂存
             └─ 模型正文暂存
                    │
                    ▼
             FreshBusinessResultGate
                ├─ 匹配：result → delta → done，并统一落库
                └─ 不匹配：清除暂存成功结果和模型正文，发送固定安全提示
```

规划只分析当前用户消息，不读取历史结果。规划结果携带本轮允许或要求的结构化结果类型，供查询执行和收尾校验共同使用。

## 5. 核心模型

### 5.1 BusinessQueryPlan

`BusinessQueryPlan` 表达三种路径：

- `GENERAL`：普通问答，不要求结构化业务结果。
- `DIRECT`：意图明确且参数完整，包含确定性命令和唯一的期望结果类型。
- `MODEL_REQUIRED`：能够确认是实时业务查询，但需要模型完成参数提取、工具选择或澄清，包含允许的结果类型集合。

计划对象只保存规范化后的业务参数，不保存认证身份、Token、输出通道或历史消息。

### 5.2 结果类型映射

| 查询能力 | 结构化结果类型 |
| --- | --- |
| 商品查询 | `product-list` |
| 订单查询 | `order-list` |
| 物流查询 | `logistics-timeline` |
| 客户查询 | `customer-list` |
| 客户订单 | `order-list` |
| 售后列表 | `after-sale-list` |
| 售后详情 | `after-sale-detail` |

结果类型是服务端白名单常量，不接受客户端或模型提交任意 kind。

## 6. BusinessQueryPlanner

`BusinessQueryPlanner` 是无状态单例，只处理当前请求正文，并返回不可变计划。

### 6.1 DIRECT 范围

第一版只接管已有确定性动作链路且可以可靠获得完整参数的三类请求：

- 完整订单号的物流查询；
- 完整客户编号的订单查询；
- 完整售后工单号的详情查询。

例如“查看售后工单 HH20260414_00002”必须规划为 `DIRECT`，并要求结果类型 `after-sale-detail`。同一编号连续查询两次时，两轮分别执行，不读取或复用上一轮结果。

识别必须同时满足业务意图词和完整标识符。控制字符、空值和超过现有长度上限的标识符不能进入 DIRECT。无法高置信识别时返回 `MODEL_REQUIRED`，不得猜测标识符类型。

### 6.2 MODEL_REQUIRED 范围

以下请求属于实时业务查询，但保留模型工具路径：

- 商品名称或编码搜索；
- 订单号、外部订单号或物流号的通用订单搜索；
- 客户姓名或客户编号的客户信息搜索；
- 带可选时间范围的客户订单查询；
- 按售后单号、订单号、客户编号或客户姓名搜索售后单；
- 不能通过高置信规则唯一映射到 DIRECT 的业务自然语言。

规划器只判断是否需要新鲜结果及允许的 kind，不承担完整参数抽取。

### 6.3 多意图请求

一句话包含多个独立查询目标时，本阶段不自动串行或并行调用多个工具。规划为 `MODEL_REQUIRED`，模型必须请求用户确认一个查询目标；如果模型擅自调用部分工具，结果 Gate 不把部分结果描述为全部完成。完整多工具编排在后续意图识别阶段设计。

## 7. DirectBusinessQueryExecutor

确定性执行器复用现有可信链路：

- 订单物流复用 `OrderQueryGateway.logistics(...)`；
- 客户订单复用 `CustomerOrderQueryService.query(...)`；
- 售后详情复用 `AfterSaleQueryGateway.detail(...)`。

执行仍使用 `ChatTurnPreparationService` 产生的 `AgentIdentity` 和 `requestId`，并继续经过组织灰度、权限范围、内部 Token、熔断、下游响应校验、字段脱敏和集合上限。执行器不接受客户端指定 Gateway、工具名、结果 kind 或组织信息。

执行成功后沿用固定顺序：

1. `ChatToolResultRecorder.prepare(...)` 校验和生成待持久化结果；
2. 将结果登记到本轮 `ChatTurnExecution`；
3. 发送 SSE `result`；
4. 发送服务端固定助手正文；
5. 由 `ChatTurnFinalizer` 在同一收尾事务中提交消息、结果和稳定历史游标。

DIRECT 调用失败时使用现有安全业务错误，不回退给模型生成查询答案。

## 8. FreshBusinessResultGate

### 8.1 本轮隔离

Gate 只检查当前 `ChatTurnExecution` 新登记的结果。历史消息结果、Redis 历史快照和摘要中的内容均不参与判断。

### 8.2 先暂存后提交

`MODEL_REQUIRED` 路径中，模型工具产生的 `ToolUiResult` 和模型正文先暂存在当前执行上下文，不立即发送给前端。工具返回给模型的有界文本保持不变，模型仍可据此生成简短概括。

模型流结束后，Gate 一次性检查：

- 至少存在一个本轮结构化结果；
- 每个准备发布的结果 kind 都属于本轮允许集合；
- 必需结果类型已经出现；
- 本轮没有发生取消、输出错误或下游失败。

检查通过后，先按产生顺序发送所有 `result`，再发送已暂存正文，最后由现有 finalizer 发送 `done`。检查失败时清除未发布的待持久化业务结果和模型正文，改用固定安全提示完成本轮。

### 8.3 固定失败提示

模型未调用工具或调用结果不匹配时，服务端返回：

> 本轮未完成实时业务查询，请补充查询条件或稍后重试。

该提示不声称查询成功、不引用历史业务值，也不伪造空卡片。失败原因仅进入安全日志和内部指标。

### 8.4 流式体验

- `GENERAL` 保持现有逐 delta 推送。
- `DIRECT` 查询完成后立即发送卡片与固定正文。
- `MODEL_REQUIRED` 为保证结果与正文原子一致，等待模型和工具完成校验后再发送卡片与正文，因此首字延迟可能增加。

该取舍只作用于实时业务查询，不影响普通问答。

## 9. 与现有 ChatTurnRunner 的衔接

`ChatTurnRunner` 仍负责单轮生命周期，但不承载具体识别规则：

1. `prepare(...)` 创建本轮消息并返回可信上下文；
2. `BusinessQueryPlanner.plan(request.message())` 生成计划；
3. DIRECT 交给确定性执行器；
4. GENERAL 使用现有 `contextService + aiChatService` 流式链路；
5. MODEL_REQUIRED 使用同一模型工具链，但输出进入 Gate；
6. 所有分支仍只从 `finally` 进入 `ChatTurnFinalizer`。

现有前端卡片动作继续由 `ChatActionDispatcher` 处理。规划器处理的是用户手工输入的消息，不改变客户端白名单动作协议。

## 10. 配置

新增 Nacos 配置，不写入 `application.properties`：

```properties
# 实时业务查询必须产生本轮新鲜结构化结果；生产环境保持开启
agent.chat.business-query-enforcement.enabled=true
```

配置关闭仅作为紧急回退手段。关闭时恢复当前模型流路径，但不改变工具自身的权限和灰度开关。配置属性必须使用专用 `@ConfigurationProperties` 类型，并在启动时完成绑定校验。

## 11. 异常处理与可观测性

### 11.1 异常策略

- 下游超时、熔断或不可用：不生成卡片，不允许模型补写业务事实。
- 模型没有调用工具：丢弃模型实时查询正文并返回固定提示。
- 模型调用错误工具：不发布错误卡片，返回固定提示。
- 结果序列化或大小校验失败：沿用现有失败收尾，不发布无法持久化的卡片。
- 用户取消：清除尚未发布的暂存正文和结果，沿用现有取消状态。
- SSE 发送失败：沿用 `OUTPUT_ERROR`，由统一收尾释放会话占用。

### 11.2 安全日志

新增日志仅记录：

- `requestId`；
- 规划类型；
- 期望结果类型集合；
- 实际结果类型集合；
- Gate 结果码；
- 规划和校验耗时。

日志禁止记录用户原文、商品关键字、订单号、物流号、客户编号、客户姓名、售后单号、内部 Token、下游响应正文或模型完整正文。

建议结果码：`GENERAL`、`DIRECT_SUCCESS`、`FRESH_RESULT_ACCEPTED`、`MISSING_RESULT`、`UNEXPECTED_RESULT`、`CANCELLED`。

## 12. 测试设计

### 12.1 规划器单元测试

- 完整订单号物流查询进入 DIRECT，期望 `logistics-timeline`。
- 完整客户编号订单查询进入 DIRECT，期望 `order-list`。
- 完整售后工单号详情查询进入 DIRECT，期望 `after-sale-detail`。
- 商品名称、客户姓名、售后时间范围查询进入 MODEL_REQUIRED。
- 普通问答进入 GENERAL。
- 空值、控制字符和超长标识符不进入 DIRECT。
- 多意图请求不被错误地规划为单一 DIRECT。

### 12.2 Gate 单元测试

- MODEL_REQUIRED 没有结果时，不发送模型成功正文，返回固定提示。
- 实际 kind 不在允许集合时，不发送错误卡片。
- 正确结果按 `result → delta` 顺序发送。
- 多个允许结果保持产生顺序。
- 取消和输出错误时不刷新暂存结果。
- GENERAL 不缓冲 delta。

### 12.3 执行链集成测试

- 连续两轮输入“查看售后工单 HH20260414_00002”，两轮分别调用 Gateway，并分别持久化新的 `after-sale-detail`。
- DIRECT 仍经过组织灰度与可信身份校验。
- DIRECT 下游失败不进入模型。
- MODEL_REQUIRED 正确调用商品、订单、客户和售后工具时，结构化结果和助手消息由同一 finalizer 提交。
- 刷新会话后，已提交卡片仍能通过历史接口恢复。
- 普通问答的首 delta、用量统计和 finishReason 行为不回归。

### 12.4 回归测试

运行 Agent Server 全量测试，并验证桌面端现有 `product-list`、`order-list`、`logistics-timeline`、`customer-list`、`after-sale-list` 和 `after-sale-detail` 解析测试。联调至少覆盖商品、订单、物流、客户、客户订单、售后列表、售后详情和重复查询。

## 13. 验收标准

1. 连续两次查询同一实时业务对象时，每轮都产生新的结构化结果记录。
2. 任何没有本轮匹配结果的实时业务请求都不能显示“已查询”或“卡片已展示”。
3. 错误工具结果不能发送到前端或写入成功助手消息。
4. DIRECT 请求不调用模型，且保留现有权限、灰度、韧性和持久化约束。
5. 普通问答继续流式输出。
6. 日志和指标不泄露业务标识符、用户原文或凭据。
7. 所有相关单元测试、集成测试和现有回归测试通过。

## 14. 发布与回退

先在本地和测试组织开启 `agent.chat.business-query-enforcement.enabled=true`，完成重复查询和历史恢复验证，再保持配置开启发布。出现紧急兼容问题时可以通过 Nacos 临时关闭总开关恢复原模型路径；工具权限、结果持久化和客户端白名单动作不随之关闭。修复问题后重新开启，不长期运行在关闭状态。
