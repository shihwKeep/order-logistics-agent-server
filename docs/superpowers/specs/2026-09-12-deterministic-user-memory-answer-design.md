# 确定性用户记忆直答设计

## 1. 背景与根因

跨会话记忆的 MySQL、Outbox、Elasticsearch、Milvus、Knowledge 召回和 Agent MySQL 终审链路均已验证正常。真实请求中，Agent 已选中 `用户常用工作范围是Java开发`，`hasUserMemoryContext=true`，该记忆也实际进入了模型请求；但相同请求在 `qwen-plus` 上既出现过正确回答，也出现过“无法获取或记忆”的拒答。

因此问题不是召回丢失，而是把明确的个人记忆问答交给通用生成模型后，结果受模型随机性和业务角色提示影响，无法达到生产级稳定性。继续追加 Prompt 或重试只能降低失败概率，不能保证确定性。

本阶段采用确定性直答：对于严格识别出的个人记忆查询，由应用服务使用已通过 MySQL 终审的记忆生成固定、安全的回答，不调用通用聊天模型；其他问题继续走现有模型链路。

## 2. 范围与非目标

本阶段包含：

1. 严格识别“询问本人已记住信息”的单一意图问题。
2. 复用现有 `UserMemoryRecallService`，不建立第二套召回或权限逻辑。
3. 从已终审、已排序的记忆中选择与问题类别匹配的记录。
4. 生成受控中文回答，并复用现有 SSE、消息落库和会话收尾流程。
5. 记录不含正文的决策日志与指标。

本阶段不修改前端，不新增数据库表，不改变显式/隐式记忆的展示和删除语义，不允许确定性直答处理订单、商品、客户、物流、售后或知识库问题，也不删除现有记忆上下文注入能力。

## 3. 方案选择

采用应用层确定性回答，而不是以下方案：

- 不采用继续增强通用 Prompt：线上已证明相同输入仍会产生不同结果。
- 不采用专用模型二次判断：仍存在概率失败，并增加一次模型延迟和成本。
- 不把记忆正文提升为 system 消息：隐式或显式记忆均属于用户来源数据，提升权限会扩大提示注入风险。

确定性直答不执行记忆正文，只把已终审记录当作待展示文本，因此既能消除模型随机性，也保持原有权限边界。

## 4. 组件边界

### 4.1 `DirectMemoryQuestionClassifier`

纯函数、无模型、无数据库。输入当前消息，输出可选的问题类型：

- `PREFERRED_NAME`：用户询问希望如何称呼自己。
- `PROGRAMMING_LANGUAGE`：用户询问自己常用的编程语言或技术语言。
- `WORK_SCOPE`：用户询问自己的工作或长期工作范围。
- `ANSWER_LANGUAGE`：用户询问自己的回答语言偏好。
- `ANSWER_STYLE`：用户询问自己的回答风格偏好。

分类器只接受短、明确、单一意图的第一人称问句。消息包含订单、物流、退款、售后、商品、客户、库存等业务词，包含多个并列问题，或无法唯一分类时返回空，继续走原链路。

### 4.2 `DeterministicUserMemoryAnswerService`

输入认证身份和当前消息：

1. 调用分类器；未命中时返回 `NOT_HANDLED`，不访问记忆服务。
2. 命中时调用现有 `UserMemoryRecallService`，沿用租户、用户、世代、状态、过期、版本、抑制和冲突终审。
3. 按问题类型过滤允许的记忆类别。
4. 选择召回结果中优先级最高的一条，返回受控回答。

问题类型与可用类别：

| 问题类型 | 可用记忆类别 |
| --- | --- |
| `PREFERRED_NAME` | `PROFILE_PREFERRED_NAME` |
| `PROGRAMMING_LANGUAGE` | `WORK_COMMON_SCOPE` |
| `WORK_SCOPE` | `WORK_COMMON_SCOPE` |
| `ANSWER_LANGUAGE` | `PREFERENCE_LANGUAGE` |
| `ANSWER_STYLE` | `PREFERENCE_ANSWER_STYLE` |

`PREFERENCE_LANGUAGE` 在现有模型中表示“偏好使用中文或英文回答”，不是编程语言，因此 `PROGRAMMING_LANGUAGE` 只能读取 `WORK_COMMON_SCOPE`。选中记录后仍需通过受控内容规则确认其中包含允许识别的技术栈或编程语言；只有“后端开发”等宽泛工作范围而没有具体语言时，返回“尚未记住”，不得自行推断。

### 4.3 `DeterministicMemoryAnswerRenderer`

渲染器只生成文本，不调用模型、不执行工具。输出规则：

- 命中：`根据您之前提供的信息，<经过安全清洗的记忆内容>。`
- 未命中：按问题类型返回固定文案，例如 `我还没有记住您常用的编程语言。`
- 召回服务全部不可用：`记忆服务暂时不可用，请稍后重试。`

正文限制长度，移除控制字符并规范句末标点；不输出 `sourceType`、类别、memory ID、分数、索引或存储实现。记忆文本不会再次作为 Prompt 发送给模型，所以其中的指令性文本不会被执行。

## 5. 请求数据流

```text
当前用户消息
  -> 显式“请记住”命令处理
  -> 卡片动作处理
  -> 实时业务查询计划
  -> DirectMemoryQuestionClassifier
       -> 非明确个人记忆问句：现有上下文准备 -> 通用模型
       -> 明确个人记忆问句：UserMemoryRecallService
            -> 匹配记忆：确定性渲染 -> SSE -> MySQL 收尾
            -> 无匹配记忆：固定“尚未记住” -> SSE -> MySQL 收尾
            -> 全部召回不可用：固定服务不可用提示 -> SSE -> MySQL 收尾
```

直答分支位于业务查询计划之后，并且只有 `BusinessQueryMode.GENERAL` 才允许进入。任何被识别为 `DIRECT`、`MODEL_REQUIRED`、卡片动作或显式记忆写入的请求都不能进入直答分支。直答仍先完成 `ChatTurnPreparationService`，因此沿用会话归属校验、请求占用、消息序号、取消和最终持久化规则。

## 6. 流式输出与状态

`ChatTurnRunner` 在通用模型调用前调用确定性服务。结果为 `HANDLED` 时：

1. 发送 `GENERATING`。
2. 发送一个受控 `delta`。
3. 写入 `execution.content` 并标记首包时间。
4. 设置 `finishReason=MEMORY_RECALLED`、`status=SUCCESS`。
5. 直接返回，由现有 `ChatTurnFinalizer` 保存助手消息并发送 `done`。

该分支不注册或执行工具，不产生结构化业务卡片，不伪造模型 Token 用量。取消、SSE 断开和持久化失败继续由现有统一收尾处理。

## 7. 安全与优先级

1. 当前用户消息、系统规则、实时业务工具和知识库证据始终高于历史记忆。
2. 只有当前认证身份范围内且通过 MySQL 终审的活动记忆可以直答。
3. 混合意图、业务意图和模糊问题一律不直答。
4. 记忆正文只作为文本展示，不作为代码、指令、工具参数或 Prompt 执行。
5. 清空全部记忆、关闭记忆或世代变更后，旧记忆不能被直答。
6. 日志只记录 request ID、问题类型、处理结果和可选的 memory ID，不记录记忆正文。

## 8. 故障处理

- 分类器未命中：完全沿用现有模型链路。
- 记忆存在但与问题类型不匹配：返回固定“尚未记住”，不得使用无关记忆推断。
- Knowledge 双路召回不可用且没有可用的全局显式记忆：返回“记忆服务暂时不可用”，不得声称用户没有该记忆。
- MySQL 终审异常：沿用召回服务 fail-safe 语义，但直答服务必须得到可区分的不可用结果；不能把基础设施失败伪装成“尚未记住”。
- 输出清洗失败：不回显原文，返回安全的服务不可用提示。

为支持上述区分，召回结果需要提供受控状态，而不是只用空列表同时表达“没有候选”“记忆关闭”和“召回失败”。状态只在 Agent 内部使用，不返回前端。

## 9. 测试与验收

### 9.1 单元测试

- 五类明确问句能够唯一分类。
- 陈述句、混合业务意图、多问题和模糊问句不分类。
- `PROGRAMMING_LANGUAGE` 只使用包含明确技术栈或编程语言的 `WORK_COMMON_SCOPE`，不会选中称呼、回答语言偏好或宽泛的“后端开发”。
- 无匹配记忆返回对应的固定“尚未记住”文案。
- 召回不可用返回服务不可用文案。
- 控制字符、超长内容和指令性文本不会被执行或泄露内部元数据。

### 9.2 执行链测试

- 命中直答时不调用 `AiChatService`、业务工具或知识库工具。
- 直答正常发送 `status/delta/done`，助手消息以 `SUCCESS` 和 `MEMORY_RECALLED` 落库。
- 未分类问题继续进入现有上下文和模型链路。
- 业务问题仍由现有 `BusinessQueryPlanner` 和证据门禁处理。
- 停止、SSE 输出失败和消息保存失败仍走统一收尾。

### 9.3 端到端验收

1. 已存在隐式记忆 `用户常用工作范围是Java开发`。
2. 新建会话询问 `我平时主要使用什么编程语言？`。
3. 连续执行至少 10 次，10 次都必须依据记忆回答 Java，且模型调用计数不增加。
4. 清空全部记忆后再次询问，必须回答尚未记住，不能使用旧索引残留。
5. 停止 Knowledge Service 后询问，必须明确提示记忆服务暂时不可用。
6. 询问退款、订单等业务问题，仍走原业务工具与知识库规则。

## 10. 实施约束

- 按测试先行实现；先证明当前执行链会调用通用模型并产生不稳定结果，再实现直答分支。
- 不修改前端和 Knowledge Service。
- 不在 Nacos 增加新的业务开关；该能力跟随现有长期记忆总开关。
- 保留现有低权限记忆上下文注入，用于非直答场景的个性化表达。
- 在自动化测试和真实依赖端到端验证都通过前，不宣称问题已经修复。
