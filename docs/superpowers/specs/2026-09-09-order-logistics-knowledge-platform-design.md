# 订单物流智能坐席知识库平台设计

## 1. 背景与目标

当前订单物流智能坐席已经具备商品、订单、物流、客户和售后业务工具，但尚未具备企业知识问答能力。本设计新增一套独立的多租户知识库平台，用于管理业务规则、操作规范、售后政策和物流说明等非结构化知识，并由 Agent 在对话中按需检索。

本期目标如下：

- 一个租户可以创建多个命名知识库，例如商品规则、订单规则、物流规则和售后规则。
- 系统管理员管理本租户知识库，超级管理员管理所有租户知识库。
- 所有已登录坐席都可以查询本租户全部已启用知识库中的已发布内容。
- 支持常见办公文档、图片和扫描件的解析、人工校正、版本化发布与回滚。
- 使用 Elasticsearch 与 Milvus 混合召回，再通过本地 Reranker 精排。
- 回答必须携带可核验的真实引用；没有可靠证据时不生成业务结论。

本期不包含跨会话用户记忆。知识库属于租户级业务知识，与会话摘要和未来的用户长期记忆相互独立。

## 2. 方案选择

### 2.1 候选方案

1. 将全部能力放入 Agent 服务：开发入口少，但解析、OCR、向量化和批量索引会增加 Agent 资源压力，影响在线聊天链路。
2. 新建独立 Knowledge Service：管理、入库与检索职责清晰，可以独立限流、恢复和扩容，Agent 只消费检索结果。
3. 直接改造现有 BizAgent：可以复用部分 RAG 代码，但现有模块同时包含 Qdrant、旧知识链路和不同的认证模型，改造边界不清晰。

### 2.2 最终选择

采用方案 2，新建以下项目：

```text
D:\GitCode\order-logistics-knowledge-service
D:\GitCode\order-logistics-agent-admin-web
```

Knowledge Service 是知识数据与检索规则的所有者；Agent 仍是对话编排和最终答案生成的所有者。

## 3. 总体架构与职责

```text
知识库管理台
   │ 登录、管理、上传、预览、发布、回滚
   ▼
Gateway
   ▼
Knowledge Service
   ├─ SSPX 认证与角色校验
   ├─ 知识库、文档和版本管理
   ├─ 解析、OCR、分块和索引任务
   ├─ 混合检索、精排和引用
   └─ 发布记录与操作审计
       │
       ├─ MySQL：元数据、版本、任务和审计
       ├─ MinIO：原始文件与解析产物
       ├─ Elasticsearch：中文 BM25 索引
       ├─ Milvus：2560 维语义向量
       ├─ PaddleOCR：扫描件与图片识别
       ├─ Ollama：Qwen3-Embedding-4B
       └─ BGE Reranker：候选精排

桌面坐席端
   ▼
Agent
   ▼ 内部检索接口
Knowledge Service
   ▼
证据片段与引用
   ▼
Agent 回答模型生成最终答案
```

Knowledge Service 不直接生成客服答案。它返回经过身份过滤、混合召回、精排和发布版本校验的结构化证据；Agent 将证据、会话上下文、系统提示词和本轮问题组合后调用回答模型。

## 4. 身份、角色与租户隔离

### 4.1 应用与角色

管理台沿用 SSPX 中“快快外卖”应用的账号体系：

- 开放应用 Client ID：`100006`。
- 业务 Application ID：`444`。
- 系统管理员角色编码：`KNOWLEDGE_ADMIN`。
- 超级管理员角色编码：`KNOWLEDGE_SUPER_ADMIN`。

Client Secret 仅通过服务端环境变量或配置中心注入，不写入源码、前端资源、日志或设计文档。

### 4.2 权限矩阵

| 身份 | 能力 |
|---|---|
| 普通已登录用户 | 通过桌面端查询本租户所有启用知识库的已发布知识 |
| `KNOWLEDGE_ADMIN` | 创建和管理本租户知识库、文档、版本、发布与回滚 |
| `KNOWLEDGE_SUPER_ADMIN` | 选择目标租户并管理任意租户知识库 |
| 同时具有两个角色 | 按超级管理员处理 |

权限判断只使用角色 Code，并校验角色属于 Application ID 444、状态有效且未删除。SSPX 角色接口不可用时，所有管理操作默认拒绝；不能因为依赖异常而放宽权限。

### 4.3 管理台登录

管理台由 Knowledge Service 提供登录会话入口：

```text
浏览器 → Knowledge Service → SSPX 快快外卖认证
       ← HttpOnly 会话 Cookie ← Redis 服务端会话
```

浏览器不在 `localStorage` 保存访问令牌。会话同时具有空闲过期时间和绝对过期时间；退出登录时清理 Redis 会话并使 Cookie 失效。

### 4.4 强制租户边界

- 普通管理员请求中的 `tenantId` 不作为授权依据，服务端强制使用登录身份中的租户。
- 超级管理员必须显式选择目标租户；审计同时记录操作者、操作者租户和目标租户。
- 知识库管理、检索、原文预览和下载接口都必须在服务端校验租户。
- 前端隐藏菜单或按钮只用于改善体验，不能代替后端鉴权。
- Agent 调用 Knowledge Service 使用内部服务凭证，并携带签名的用户与租户声明；客户端不能自行传入可信租户头。

## 5. 存储设计

### 5.1 MySQL

在当前 MySQL 实例中新建独立数据库：

```text
order_logistics_knowledge
```

核心表如下：

| 表 | 作用 |
|---|---|
| `kb_knowledge_base` | 知识库名称、租户、状态和检索配置 |
| `kb_document` | 文档逻辑身份、分类及当前草稿/发布版本指针 |
| `kb_document_version` | 上传、重新解析或人工校正形成的不可变版本 |
| `kb_document_unit` | 页、工作表、幻灯片等可定位原文单元 |
| `kb_chunk` | 分块正文、来源位置、Token 数和内容哈希 |
| `kb_ingestion_task` | 解析、OCR、分块、向量化和索引任务 |
| `kb_outbox_event` | 与业务事务同时写入的任务唤醒事件 |
| `kb_publish_record` | 发布、回滚和停用记录 |
| `kb_audit_log` | 创建、修改、删除、发布等操作审计 |
| `kb_search_log` | 数量、耗时、结果与降级状态，不保存问题和正文 |

所有业务表都带 `tenant_id`。可变聚合根使用乐观锁版本字段；删除采用软删除，历史版本、发布记录和审计记录不物理删除。

`kb_document` 至少保存以下两个版本指针：

```text
current_draft_version_id
current_published_version_id
```

新版本处理期间，线上继续查询旧版本。

### 5.2 MinIO

知识文件使用独立 MinIO 服务，不复用 Milvus 内部 MinIO。单独的对象存储便于权限隔离、备份和生命周期管理。

对象键必须包含租户和版本：

```text
tenant/{tenantId}/knowledge-base/{kbId}/document/{documentId}/version/{versionId}/source
tenant/{tenantId}/knowledge-base/{kbId}/document/{documentId}/version/{versionId}/parsed
```

数据库保存对象键，不保存可长期访问的公开 URL。预览和下载通过后端授权接口生成短期地址。

### 5.3 Elasticsearch 与 Milvus

- Elasticsearch 保存标题、正文、来源位置和版本元数据，索引使用 `ik_max_word`，查询使用 `ik_smart`。
- Milvus 保存 Qwen3-Embedding-4B 生成的 2560 维向量及必要过滤字段。
- 草稿检索与线上发布检索使用独立逻辑索引/Collection，避免草稿进入坐席问答。
- 索引是可重建派生数据，MySQL 中的发布指针始终是业务真相。

## 6. 文档与版本状态

一个租户可以创建多个知识库。知识库分别维护文档和启用状态，但桌面端默认统一检索本租户所有启用知识库。

版本处理状态为：

```text
UPLOADED
→ PARSING
→ OCR_PROCESSING（仅需要 OCR 时）
→ CHUNKING
→ INDEXING
→ READY
→ PUBLISHED
→ ARCHIVED
```

任一步骤不可恢复失败时进入 `FAILED`，记录失败阶段、稳定错误码、重试次数和脱敏错误摘要。

管理员可以在发布前修改解析或 OCR 正文。修改不会覆盖原始解析结果，而是生成新的人工校正版，记录修改人、修改时间和差异。校正会使当前草稿 Chunk 与索引失效，并重新执行分块、Embedding 和索引。

只有最新且状态为 `READY` 的草稿版本可以发布。已发布版本不受后续草稿修改影响。

## 7. 异步入库与任务恢复

采用“MySQL 任务为准、RabbitMQ 负责快速唤醒”的模式：

```text
上传文件
→ MinIO 保存原文件
→ MySQL 短事务创建文档版本、处理任务和 Outbox 事件
→ 事务提交
→ Outbox 投递 RabbitMQ
→ Worker 领取数据库任务租约
→ 解析/OCR
→ 规范化正文
→ 分块
→ 生成向量
→ 写入草稿索引
→ READY
→ 管理员手动发布
```

关键约束：

- RabbitMQ 只负责通知，数据库任务是唯一任务真相。
- 即使消息丢失，定时扫描器也能从 MySQL 重新发现待处理任务。
- Worker 使用 `lease_token`、`locked_by` 和 `locked_until` 竞争与续租，避免并发重复执行。
- 任务阶段均有稳定幂等键，服务重启后从未完成阶段恢复。
- OCR 按页执行，单页失败可以单独重试。
- Embedding 使用小批次和有界并发，避免占满 32 GB 内存和 6 GB 显存。
- 在线查询优先级高于后台文档入库。
- 自动重试达到上限后任务进入 `DEAD`，管理员可查看原因并手动重试。

## 8. 文档格式、解析与 OCR

首期完整支持：

- PDF，包括扫描版 PDF。
- DOCX。
- XLS、XLSX、CSV。
- PPTX。
- TXT、Markdown、HTML。
- PNG、JPG、JPEG 等常见图片。

解析规则：

- PDF 优先读取文本层；文本缺失、乱码或文本密度过低的页面转交 OCR。
- DOCX 保留标题层级、段落、列表和表格。
- Excel/CSV 按工作表和表格区域解析，表格数据保留表头。
- PPTX 按幻灯片提取标题、正文、表格和备注；图片区域调用 OCR。
- HTML 删除脚本、样式、导航等噪声，保留标题和正文结构。
- 图片直接调用 OCR。

OCR 使用独立 PaddleOCR HTTP 服务。Knowledge Service 传入页面或图片，OCR 返回文字、文本框位置和置信度。PaddleOCR 的 Python、模型和图像处理依赖不进入 Java 服务。

低置信度 OCR 内容在管理台突出显示，发布前提醒管理员核对。OCR 失败页面不能被静默跳过。

## 9. 分块设计

分块顺序如下：

```text
标题层级
→ 段落边界
→ 列表和表格边界
→ Token 长度兜底切分
```

初始参数：

```text
目标 Chunk：约 500 Token
最大 Chunk：约 800 Token
相邻重叠：约 80 Token
```

参数由配置中心管理，并将策略版本写入文档版本。调整策略后可以按版本执行重建。

特殊规则：

- 标题路径自动附加到 Chunk，避免正文脱离主题。
- 订单号、商品编码和政策编号等完整标识不能从中间切断。
- 表格 Chunk 重复携带表头，避免数据行失去字段含义。
- Chunk 保存页码、工作表、幻灯片、段落和字符范围等定位信息。
- 原始解析文本、人工校正文和最终 Chunk 分别保存，保证可追溯。

## 10. Embedding 与本地资源策略

Embedding 最终采用 Ollama 上的：

```text
qwen3-embedding:4b-q4_K_M
```

模型输出使用 2560 维向量，新建独立 Milvus Collection，不能与既有 1024 维或其他语义空间的向量混用。

当前开发机器为 i7-11800H、32 GB 内存和 RTX 3060 Laptop 6 GB 显存。4B Q4 模型适合该机器，但需控制后台批次与并发。首期按以下原则运行：

- 单批 Embedding 数量有上限，初始建议 8 个 Chunk。
- Chunk 本身遵守 800 Token 上限，不使用模型最大上下文作为分块目标。
- 入库任务采用有界线程池和背压。
- 模型名、向量维度、查询指令和分块策略都写入版本元数据。
- 更换模型或维度时创建新 Collection 并全量重建，禁止在同一 Collection 混用。

## 11. 混合检索与精排

线上检索流程：

```text
用户问题
→ 身份与 tenantId 校验
→ 查询规范化和关键词提取
→ Qwen3-Embedding-4B 生成查询向量
→ Milvus 语义召回 Top 30 ┐
                          ├→ RRF 融合去重 Top 20
→ Elasticsearch 召回 Top 30 ┘
→ BAAI/bge-reranker-v2-m3 精排
→ 相关性门控
→ 最终证据 Top 5
→ 返回 Agent
```

Milvus 处理语义改写，Elasticsearch 处理精确业务词、政策编号和商品编码。两种原始分数不可直接比较，使用 RRF 按排名融合，初始 RRF 常数取 60。所有数量和阈值均可配置，并通过真实客服问题评测后调整。

桌面端检索范围是当前租户全部启用知识库中的已发布版本。管理台检索测试可以限定租户、知识库或草稿版本。

检索返回示例：

```json
{
  "answerable": true,
  "evidences": [
    {
      "chunkId": "chunk-32001",
      "content": "订单签收后七日内满足条件的商品可以申请退款。",
      "documentTitle": "售后退款规则",
      "pageNumber": 3,
      "score": 0.91
    }
  ]
}
```

`documentTitle`、位置和 Chunk 身份由服务端生成，模型不能自行构造引用。没有 Chunk 达到可靠阈值时返回 `answerable=false`；Agent 明确回复“知识库中暂未找到相关规定”，不根据模型常识补充业务规则。

## 12. 发布、回滚与一致性

MySQL 的 `current_published_version_id` 是唯一发布真相。发布流程为：

```text
1. 检查草稿版本为 READY
2. 将新版本 Chunk 幂等写入 Elasticsearch 发布索引
3. 将新版本向量幂等写入 Milvus 发布 Collection
4. 校验两边 Chunk 数量与内容哈希
5. MySQL 短事务切换 current_published_version_id
6. 异步清理旧版本发布索引数据
7. 写入发布记录和审计日志
```

每个索引记录使用稳定幂等主键：

```text
tenantId + documentId + versionId + chunkIndex
```

第 5 步之前，新版本即使已写入发布索引，也不能作为有效证据。在线召回候选经过 Reranker 后，还必须批量查询 MySQL 校验候选的 `versionId` 是否等于文档当前发布版本。该最终校验不依赖可能过期的缓存，因此发布切换后不会引用旧版本。

检索阶段预留额外候选。最终版本校验过滤掉失效记录后，按照原排序继续补足，最多返回配置的证据数量；如果剩余证据不足，则按照低相关性规则返回不可回答，不能用失效版本凑数。

新版本写入后才切换数据库指针，避免发布后缺少索引；旧版本在指针切换后再清理，避免更新期间无内容可查。短暂存在的新旧索引重复记录会被最终版本校验过滤。

回滚先确保目标历史版本完整进入两套发布索引，校验成功后再切换 MySQL 指针。停用文档或知识库先修改 MySQL 有效状态，使在线最终校验立即拒绝，再异步清理索引。

## 13. 故障与降级

### 13.1 入库严格模式

- MinIO、解析、OCR、Embedding、Elasticsearch 或 Milvus任一步骤失败，版本不能进入 `READY`。
- OCR 失败页面不能跳过，ES 与 Milvus 数量或哈希校验不一致时不能发布。
- 失败任务自动重试，超过上限后进入 `DEAD` 并等待人工处理。

### 13.2 查询受控降级

```text
正常：Milvus + Elasticsearch → RRF → Reranker
ES 异常：Milvus → Reranker
Milvus或Embedding异常：Elasticsearch → Reranker
Reranker异常：仅接受满足更严格“双路命中”规则的 RRF 结果
两路召回都异常：返回知识服务暂不可用
```

如果 Reranker 与任一路召回同时不可用，则无法满足双路命中门控，返回无可靠证据。降级不能绕过租户、发布版本和引用校验。

所有降级都记录稳定结果码、组件、耗时和 Trace 标签，不记录用户问题或知识正文。

## 14. 管理台设计

管理台采用独立 Vue 3、TypeScript、Vite Web 项目，包含：

- 登录页。
- 知识库列表及新建、编辑、启用、停用。
- 文档上传、版本记录和处理进度。
- 解析/OCR预览、低置信度提示和人工校正。
- 手动发布、版本回滚、失败重试。
- 检索测试与 ES、Milvus、RRF、Reranker 各阶段诊断。
- 发布记录和操作审计。
- 超级管理员租户切换。

文档预览采用左右分栏：左侧展示原始 PDF、PPTX 或图片，右侧展示解析正文、Chunk 和来源位置。普通管理员不能切换租户；超级管理员切换租户后，所有列表与操作明确显示目标租户。

## 15. 桌面端引用展示

Agent 根据 Knowledge Service 的证据生成回答后，在桌面端答案下展示引用卡片：

```text
参考来源
1. 《售后退款规则》第 3 页
2. 《物流异常处理规范》第 7 页
```

点击引用打开只读预览，并定位到对应页、幻灯片或工作表。普通用户看不到内部检索分数和 Chunk ID。预览接口重新校验当前用户租户与文档发布状态，不使用永久公开 MinIO 地址。

## 16. API 边界

### 16.1 管理 API

管理 API 覆盖：

- 登录、退出和当前身份。
- 知识库 CRUD 与启停。
- 文档上传、列表、详情和版本列表。
- 处理任务状态、失败详情和手动重试。
- 原文、解析文本和 Chunk 预览。
- 人工校正、发布、回滚和停用。
- 检索测试与审计查询。

所有写接口支持幂等请求号，发布、回滚、删除和重试采用明确动作接口，不通过模糊的通用更新接口表达。

### 16.2 Agent 内部 API

Agent 只依赖稳定的内部检索契约：

```text
POST /internal/v1/knowledge/retrieve
```

请求包含签名身份、问题、候选上限和可选知识库范围；响应包含 `answerable`、证据、来源、使用的检索策略和受控降级状态。Agent 不依赖 Knowledge Service 的数据库实体或索引实现。

### 16.3 预览 API

引用预览使用短期、一次性或短时有效的授权标识。授权记录绑定用户、租户、文档版本和来源位置；禁止前端通过修改 URL 参数读取其他租户或草稿文件。

## 17. 安全与内容治理

- 上传时校验扩展名、MIME、文件签名和大小，文件名不参与对象路径拼接。
- 解析器与 OCR 运行在受限进程或容器中，设置 CPU、内存、页数、时间和并发上限。
- 知识正文属于不可信数据；Prompt 明确将其视为证据而不是系统指令，防止文档中的提示注入覆盖系统规则。
- 日志不记录完整文件、正文、用户问题、向量、Cookie、Token 或 Client Secret。
- 人工校正、发布、回滚、停用和跨租户访问都写审计。
- 删除采用软删除；对象与索引的物理清理由后台生命周期任务完成。

## 18. 监控指标

重点指标包括：

- 文档处理成功率、失败阶段和平均耗时。
- OCR 页数、低置信度页数、失败率和耗时。
- Embedding 批次大小、排队时间、推理时间和失败率。
- ES/Milvus 写入、查询耗时和错误率。
- Reranker 耗时、阈值淘汰数量和降级次数。
- 知识问答命中率、拒答率和引用数量。
- 发布、回滚、失败任务与过期租约数量。
- 各租户文档数、文件容量、Chunk 数和查询用量。

## 19. 测试策略

- 单元测试：权限判断、状态机、分块、RRF、版本切换和引用映射。
- 解析测试：覆盖各格式的正常、空白、损坏、超大和混合内容样本。
- OCR测试：覆盖扫描 PDF、旋转图片、低清图片、中英文混排和表格。
- 集成测试：覆盖 MySQL、MinIO、RabbitMQ、Elasticsearch、Milvus与任务租约恢复。
- 契约测试：覆盖 PaddleOCR、Ollama Embedding、Reranker 和 Agent 内部检索 API。
- 安全测试：覆盖跨租户读取、伪造租户、普通用户管理、角色失效和下载授权过期。
- 故障测试：覆盖依赖超时、单路召回失败、Worker 执行中重启和消息丢失。
- 前端测试：覆盖上传、预览、校正、发布、回滚、租户切换和引用定位。
- 离线检索评测：建立真实客服问答集，持续统计 Recall@K、首条命中率、拒答率和无依据回答率。

## 20. 验收标准

1. 所有约定格式都能上传、解析、预览并手动发布。
2. 扫描 PDF、普通图片和 PPTX 图片能够通过独立 PaddleOCR 服务识别。
3. OCR 低置信度内容可识别、校正、重新分块和重新索引。
4. 新版本处理期间旧版本持续可查，发布与回滚不会产生错误版本引用。
5. 系统管理员与超级管理员权限边界正确，普通用户不能进入管理功能。
6. 桌面端只能检索当前租户的已发布知识。
7. 回答携带可点击、可定位并经过权限校验的真实引用。
8. 无可靠证据时不生成业务规则。
9. 单个检索组件故障时按照受控策略降级，两路召回均不可用时返回明确错误。
10. 服务或 Worker 重启后，未完成任务可以通过数据库任务和租约机制继续处理。

## 21. 实施拆分

该设计是一项平台级能力，实施计划按以下可独立验收的工作流拆分，但所有工作流遵循本文统一数据和接口契约：

1. Knowledge Service 基础工程、数据库、认证授权和知识库 CRUD。
2. MinIO、文档版本、解析、PaddleOCR 和人工校正。
3. 分块、Qwen3 Embedding、Elasticsearch、Milvus与异步任务。
4. 混合检索、RRF、Reranker、发布一致性与故障降级。
5. 管理台登录、知识库/文档/任务/预览/发布页面。
6. Agent 知识工具接入、回答门控和桌面端引用卡片。
7. 端到端验收、检索评测、监控和运行文档。

每个工作流完成后均先执行自动化验证，再进入下一工作流；不通过临时硬编码绕过租户、发布版本或证据门控。
