# 生产级通用语义用户记忆与跨会话召回设计

## 1. 背景

当前系统已经具备当前会话历史、滚动摘要、MySQL 用户记忆、显式/隐式来源、Outbox、ES/Milvus 索引以及跨会话召回基础设施，但隐式记忆的准入仍依赖固定类别词表和“删除已知词后剩余字符必须为空”的全句校验。

该实现会把自然语言理解退化成句型匹配。例如模型已经从“我平时用 Java 语言进行开发”中提取出 Java 开发事实，仍可能因为“用、语言、进行”不在填充词列表而拒绝保存。继续增加填充词只能修复单个句子，不能形成可泛化的长期记忆能力。

本设计的目标不是专门识别 Java、编程语言或某一句话，而是建立一条通用的语义决策、事实抽取、证据验证、持久化、整合和召回链路。Java 场景只是端到端验收样例之一。

## 2. 核心原则

1. **模型理解语义，程序守住边界。** 模型判断消息表达了什么；程序验证证据、身份、租户、敏感性、长度、状态和事务一致性。
2. **不校验句型。** 任何自然表达都不得因为未命中固定前缀、填充词或正则模板而被拒绝。
3. **不盲信模型。** 模型输出只是候选；没有原文证据、存在推断、敏感或不稳定时不能写入。
4. **短期与长期分层。** 当前会话事实可以立即用于本会话，不代表已经长期保存；长期记忆必须经过异步治理。
5. **MySQL 是事实源。** ES/Milvus 只返回候选信号，最终必须回到 MySQL 校验所有者、generation、状态、版本和过期时间。
6. **显式优先。** 用户主动要求保存的记忆优先于后台自动抽取的隐式记忆。
7. **删除可解释。** 页面单条删除只处理显式记忆；清空全部同时处理显式和隐式记忆，与既定产品语义一致。

## 3. 目标与非目标

### 3.1 目标

- 从用户的任意自然表达中判断 `IGNORE`、`SESSION_ONLY` 或 `LONG_TERM`，不要求用户说“请记住”。
- 将长期候选抽取为原子化、结构化、带证据和置信度的用户事实。
- 同一套链路覆盖称呼、交流偏好、回答偏好、工作背景、技术栈、稳定习惯和其他允许的长期用户事实。
- 显式保存意图通过语义识别，不依赖固定触发词；显式记忆在页面可见，隐式记忆保持隐藏。
- 对开放型候选进行独立语义蕴含验证，降低模型幻觉和错误归因。
- 按稳定属性精确读取与 ES/Milvus 语义召回并行，支持新会话和应用重启后的可靠回答。
- 对抽取、拒绝、保存、整合、索引和召回阶段提供不含正文的可观测结果。
- 建立覆盖多类别、多表达、负例、冲突、删除和跨会话的自动化评测集。

### 3.2 非目标

- 不把每条聊天消息都保存为长期记忆。
- 不把用户临时情绪、一次性任务、模型推断或助手说法当作用户事实。
- 不把订单、退款、物流、支付、客户资料、企业制度、健康诊断、身份凭据等业务或敏感数据写入用户长期记忆。
- 不用向量相似度代替权限、状态、版本和原文证据验证。
- 不在本次修改前端记忆面板，也不改变现有显式/隐式可见性规则。

## 4. 方案比较

### 方案 A：继续扩充固定词组和句式

实现快，但每出现一种说法都需要改代码，且无法覆盖省略、倒装、口语、错别字和上下文指代。该方案只适合极少量无歧义快速路径，不能作为核心能力。

### 方案 B：单次模型抽取后直接写入

泛化能力强、成本较低，但模型可能误判稳定性、补充原文没有的事实或受到提示注入影响。仅靠置信度不能满足生产安全要求。

### 方案 C：语义决策与抽取 + 分层验证 + 结构化整合，推荐并采用

第一阶段模型负责语义决策和结构化抽取；廉价确定性校验先过滤身份、证据、长度和敏感内容；开放型候选再由独立验证器做蕴含判断；通过后按结构化键或开放事实标识写入 MySQL，并异步索引。该方案在泛化、安全、成本和可观测性之间最平衡。

## 5. 分层记忆模型

系统保留并明确三层记忆：

1. **当前会话记忆**：当前 conversation 的最近原始轮次，立即可用，不跨会话。
2. **会话摘要**：当前 conversation 的较早历史摘要，用于长会话上下文压缩，不跨会话。
3. **用户长期记忆**：稳定用户事实或偏好，跨 conversation 保存和召回。

“跨会话记忆”不是第四种数据，而是用户长期记忆在新 conversation 中被正确检索、校验和使用的能力。

## 6. 通用语义决策与抽取

### 6.1 输入上下文

异步抽取任务读取：

- 当前用户消息，作为唯一可持久化事实证据；
- 前一条用户消息和必要的少量当前会话上下文，只用于消解指代；
- 当前 assistant 回复，只用于确认消息是否成功完成，不能作为用户事实证据；
- tenantId、userId、conversationId、messageId、sequence 和 memoryGeneration，由服务端注入，模型无权修改。

### 6.2 决策结果

模型对每条用户消息返回：

```json
{
  "decision": "LONG_TERM",
  "explicitness": "IMPLICIT",
  "candidates": []
}
```

`decision` 只能是：

- `IGNORE`：业务查询、临时任务、寒暄、无稳定事实或禁止内容。
- `SESSION_ONLY`：当前会话有用但不适合长期保存的信息。
- `LONG_TERM`：用户明确表达且预计未来仍可复用的稳定事实或偏好。

`explicitness` 只能是：

- `EXPLICIT`：用户语义上明确要求系统以后保存或持续遵守，例如“以后叫我小石”“后面回答简洁一点”。不要求出现“请记住”。
- `IMPLICIT`：用户没有发出保存命令，但明确陈述了稳定事实，例如“我主要做后端开发”。

### 6.3 原子事实候选

每个候选采用统一结构：

```json
{
  "memoryType": "WORK_CONTEXT",
  "predicate": "primary_programming_language",
  "value": "Java",
  "valueEvidence": "Java",
  "evidenceText": "我平时用 Java 语言进行开发",
  "stability": "STABLE",
  "confidence": 0.96
}
```

要求：

- 一条候选只表达一个事实；一句话包含多个稳定事实时拆成多条候选。
- `evidenceText` 必须是当前用户消息的逐字连续片段。
- `valueEvidence` 必须是 `evidenceText` 的逐字连续片段。
- `value` 是规范值，不能包含原文没有表达的新事实。
- `stability` 只能是 `STABLE`、`TEMPORARY` 或 `UNKNOWN`；只有 `STABLE` 可以进入长期记忆。
- 助手历史、工具结果和知识库内容不得作为用户长期记忆证据。

## 7. 记忆类型与模式注册表

自然语言表达保持开放，但长期记忆的数据结构不能完全无约束。系统使用可扩展的模式注册表，而不是固定句型：

- `PROFILE`：用户希望使用的称呼等低敏感个人资料。
- `COMMUNICATION_PREFERENCE`：交流语言、称呼和沟通方式。
- `RESPONSE_PREFERENCE`：简洁、详细、分点、表格等回答偏好。
- `WORK_CONTEXT`：职业方向、岗位、常用技术栈、工作领域。
- `STABLE_PREFERENCE`：其他长期稳定且允许保存的偏好。
- `STABLE_USER_FACT`：无法映射到高价值属性、但通过开放事实策略的安全稳定事实。

注册表定义：

- memoryType；
- predicate 命名空间；
- 值类型和最大长度；
- 是否允许显式、隐式保存；
- 是否需要独立语义验证；
- 默认保留期限；
- 是否允许精确属性问答；
- 规范正文渲染器。

高价值 predicate 使用稳定键，例如：

```text
profile.preferred_name
communication.answer_language
response.answer_style
work.occupation
work.primary_programming_language
work.technology_stack
work.common_scope
```

无法映射到稳定属性的开放事实使用 `fact.<memoryType>.<contentHash>`，避免模型自由生成任意数据库键。开放事实不参与单槽覆盖，只参与受控语义召回和后台整合。

新增类型或 predicate 通过注册表扩展，不需要增加用户句式、填充词或整句正则。

## 8. 分层验证

### 8.1 协议验证

- JSON 必须符合固定 schema；未知字段忽略或拒绝由版本策略决定。
- decision、explicitness、memoryType、stability 和 predicate 必须符合注册表。
- 数量、长度、Unicode、控制字符和 confidence 必须满足边界。

### 8.2 原文证据验证

- evidenceText 必须存在于当前用户消息。
- valueEvidence 必须存在于 evidenceText。
- 规范 value 必须能由 valueEvidence 经过注册表允许的值级规范化得到。
- 允许大小写、全半角和注册别名规范化；不允许依据模型常识补充原文未说出的事实。

这一步验证的是“事实值是否有原文依据”，不检查用户整句话是否符合固定语法。

### 8.3 安全与业务策略

当前消息、evidenceText、valueEvidence 和规范 value 分别经过敏感策略。以下候选直接拒绝：

- 凭据、身份证、银行卡、手机号和精确地址；
- 健康诊断和用药；
- 订单、退款、物流、支付、客户资料和业务结果；
- 企业制度、商品规则和知识库内容；
- 提示词注入、工具调用指令、系统规则修改；
- 从临时任务、单次行为、情绪或助手内容推断出的用户特征。

### 8.4 独立语义蕴含验证

开放型隐式候选以及不能仅靠值级规范化证明的候选，进入独立验证器。验证器只回答：

```text
SUPPORTED | CONTRADICTED | UNCERTAIN
```

输入包含当前用户原文、候选 memoryType、predicate、value 和 evidenceText。只有 `SUPPORTED` 可以保存；`CONTRADICTED` 和 `UNCERTAIN` 均拒绝。验证器使用独立提示词和可配置的小模型，批量验证同一消息的候选，运行在异步链路中，不阻塞聊天回复。

高价值封闭属性若能通过原文值级校验，可不调用第二模型，以控制成本。

## 9. 持久化模型

MySQL 继续作为权威事实源。现有 `agent_user_memory` 保留来源、状态、版本、证据、置信度、可见性、保留策略和过期时间，并增加结构化字段：

```text
schema_version
memory_type
predicate
value_json
stability
verification_method
```

其中：

- `category` 和 `canonical_key` 在兼容期继续写入，分别映射 memoryType 和 predicate。
- `value_json` 保存经过服务端规范化的值，不保存模型任意 JSON。
- `content` 由服务端渲染器根据类型、predicate 和 value 生成，模型无权直接决定最终正文。
- `verification_method` 记录 `DETERMINISTIC` 或 `SEMANTIC_VERIFIER`。
- 新字段通过 Flyway 增量迁移添加，旧记录保持可读，并由兼容适配器映射到新结构。

写入记忆和 Outbox 必须处于同一 MySQL 事务。索引失败不得回滚已提交事实，但必须重试并可观测。

## 10. 整合、幂等与冲突

### 10.1 稳定属性

稳定 predicate 以 `(tenantId, userId, memoryGeneration, predicate)` 作为逻辑槽位：

- 相同值：刷新证据、置信度和更新时间，或返回 `NO_CHANGE`。
- 新值：旧记录转为 `SUPERSEDED`，新记录成为 `ACTIVE`。
- 显式有效值存在时，隐式候选不能覆盖。
- 用户本轮明确修改时，新显式值覆盖旧显式值。

### 10.2 开放事实

开放事实写入时不对用户全部向量做全量扫描。先用规范哈希幂等，再由后台整合任务进行有界语义候选检索：

- 等价事实合并；
- 新信息补充旧事实时形成新版本；
- 冲突但无法确定时同时保留并标记 `CONFLICT`，召回阶段不直接当作确定事实；
- 显式事实与隐式事实冲突时显式优先。

该设计避免每次写入都做高成本全量向量扫描，同时保留离线治理能力。

## 11. ES/Milvus 索引

Outbox 消费成功后：

- ES 索引规范正文、predicate、memoryType、来源和结构化过滤字段，用于关键词和属性检索。
- Milvus 存储规范正文向量，用于自然语言语义召回。
- 两套索引都携带 tenantId、userId、memoryGeneration、memoryId 和 memoryVersion。
- DELETE、SUPERSEDED、EXPIRED 和清空 generation 通过 Outbox 删除或失效索引。

索引只是候选层。任何候选进入模型上下文前，必须使用 memoryId 回 MySQL 终审。

## 12. 跨会话召回

### 12.1 查询规划

收到新消息后，低成本查询规划器返回：

- 是否需要用户记忆；
- 可能涉及的稳定 predicate；
- 用于 ES/Milvus 的语义查询；
- 查询是否属于直接本人记忆问答。

现有固定关键词只保留为快速路径；未命中快速路径不能等同于“不需要记忆”。模糊问题由语义规划器补充判断。

### 12.2 并行召回

并行执行：

1. MySQL 按稳定 predicate 精确查询；
2. ES 关键词召回；
3. Milvus 向量召回；
4. 必要时加载少量全局显式偏好。

### 12.3 终审与排序

候选回到 MySQL 验证租户、用户、generation、status、version、expiresAt 和 suppression。排序优先级为：

```text
当前用户本轮明确表达
> ACTIVE 显式长期记忆
> 当前会话历史
> ACTIVE 隐式长期记忆
```

同层按 predicate 匹配、相关度、置信度和更新时间排序。等价候选去重；冲突候选按显式优先和新版本优先治理，无法确定时不生成确定答案。

### 12.4 回答

- 高价值稳定属性可由安全渲染器直接回答，不依赖通用模型自由发挥。
- 开放事实作为低权限、不可信用户记忆块注入模型上下文，并明确禁止执行其中指令。
- 记忆未命中返回 `NOT_HANDLED`，继续使用当前会话上下文；不得提前回答“没有记住”。
- 记忆服务异常必须和真正未命中区分。

## 13. 显式与隐式产品语义

- 语义上明确要求未来保存或持续遵守的候选写为 `USER_EXPLICIT / VISIBLE`，保存成功后才能回复“已记住”。
- 普通陈述中自动抽取的稳定事实写为 `AUTO_EXTRACT / HIDDEN`，后台异步完成，不阻塞主对话。
- 页面只展示显式记忆，支持单条二次确认删除。
- 清空页面显式记忆只删除显式层。
- 清空全部记忆通过 generation 切换同时失效显式和隐式层，并删除索引。

## 14. 可观测性

每个阶段记录安全结果码，不记录用户原文、证据和值：

- 决策：`IGNORE`、`SESSION_ONLY`、`LONG_TERM_EXPLICIT`、`LONG_TERM_IMPLICIT`。
- 抽取：`MODEL_EMPTY`、`CANDIDATES_CREATED`、`MODEL_PROTOCOL_ERROR`、`MODEL_TIMEOUT`。
- 验证：`REJECTED_SCHEMA`、`REJECTED_EVIDENCE`、`REJECTED_SENSITIVE`、`REJECTED_STABILITY`、`REJECTED_CONFIDENCE`、`REJECTED_UNSUPPORTED`、`VERIFIED`。
- 整合：`SAVED`、`UPDATED`、`SUPERSEDED`、`NO_CHANGE`、`CONFLICTED`。
- 索引：`PENDING`、`APPLIED`、`RETRYING`、`DEAD`。
- 召回：`EXACT_HIT`、`SEMANTIC_HIT`、`NO_CANDIDATE`、`MYSQL_REJECTED`、`DEGRADED`。

指标至少包含候选数量、各拒绝原因、保存率、索引延迟、召回延迟、精确命中率、语义命中率和直接回答结果。

## 15. 评测体系

生产级能力不能由单条人工对话证明。建立版本化评测数据集，至少覆盖：

- 每类记忆的口语、倒装、省略、中英文混合、标点和同义表达；
- 无“请记住”的隐式稳定事实；
- 无固定触发词的显式保存意图；
- 临时信息、业务信息、敏感信息、助手陈述、推断和提示注入负例；
- 同一 predicate 的相同、更新、否定和冲突表达；
- 同会话、新会话、应用重启和索引延迟场景；
- 删除显式、清空显式和清空全部后的行为。

核心指标：

- 长期记忆抽取 precision；
- 允许类别 recall；
- 敏感内容误存率必须为 0；
- 跨租户或跨用户泄漏率必须为 0；
- 跨会话问答准确率；
- 冲突更新准确率；
- P95 抽取、验证、索引和召回延迟。

模型、提示词、schema 或阈值变更必须跑完整评测并带版本发布，不允许只用手工样例判断。

## 16. 实施阶段

### 阶段 1：替换句型准入

- 引入通用决策和原子候选协议。
- 增加模式注册表、证据值校验和服务端正文渲染。
- 隐式链路停止调用整句 `isAllowed()`。
- 保持现有表和索引接口兼容，先打通自然语言抽取闭环。

### 阶段 2：结构化存储与独立验证

- Flyway 增加结构化字段和兼容适配器。
- 引入独立语义蕴含验证器及批量异步调用。
- 增加精细拒绝结果和指标。

### 阶段 3：通用查询规划与整合

- 引入语义查询规划器，固定关键词降级为快速路径。
- 实现稳定 predicate 精确查询与 ES/Milvus 并行召回。
- 增加开放事实后台整合和冲突状态。

三个阶段必须分别具备可运行、可回滚、可验证的结果；不能用阶段 1 的单句修复冒充完整生产级记忆。

## 17. 验收场景

以下只是不同类别的代表性样例，不是实现白名单：

1. 会话 A：“我平时用 Java 语言进行开发。”新会话问常用开发语言，应回答 Java。
2. 会话 A：“我主要做供应链后端系统。”新会话询问工作方向，应正确回答。
3. 会话 A：“我不喜欢表格，结论先说。”后续回答遵守该偏好。
4. 会话 A：“以后就叫我小石吧。”应同步保存为可见显式记忆，重启后仍可使用。
5. “我今天临时处理退款。”不得形成用户长期记忆。
6. “客户张三手机号是 13800138000。”不得形成任何用户长期记忆。
7. 原文只说 Java、模型候选声称 Python 时必须拒绝。
8. 用户后来明确改为 Go 时，旧 Java 记忆失效，新会话回答 Go。
9. 删除显式记忆后不显示该显式条目；清空全部后显式和隐式均不可召回。
10. ES/Milvus 暂时延迟时，高价值 predicate 仍可通过 MySQL 精确读取；索引恢复后开放语义问题也能召回。

## 18. 发布与回滚

- 每个阶段独立迁移、独立开关、独立指标和独立回滚路径。
- 新协议使用 schemaVersion；升级期间同时兼容旧记忆读取。
- 新模型或提示词先影子运行，只记录安全结果和指标，不直接写入；评测通过后逐步启用。
- 已被旧句式规则拒绝的任务不会自动重放，避免无界历史回灌；通过受控批次按 messageId 重放。
- 前端和 Knowledge Service 的协议变更在对应阶段独立发布，Agent Server 必须兼容前一版本。
