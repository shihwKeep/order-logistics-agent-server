# Agent 全链路评测与可观测性设计

## 1. 背景与目标

当前系统已经具备流式对话、意图规划、业务工具调用、知识库检索、短期记忆、会话摘要、跨会话长期记忆、Redis Stream 断点续传和分布式取消能力，也在局部使用了 Micrometer 指标与结构化任务状态。然而这些能力仍分散在不同服务和业务模块中，尚未形成一套能够回答以下问题的生产体系：

- 一次回答为什么选择了当前意图、工具、知识证据和用户记忆。
- 最终回答是否忠于工具结果和知识证据，是否发生幻觉或越权。
- 网络断开、工具超时、记忆索引滞后或发布切换时，问题发生在哪个阶段。
- 某次模型、Prompt、检索策略或配置变更是否造成质量回退。
- 每轮对话消耗了多少时间、Token、外部调用和费用。
- 系统是否达到发布门禁要求，故障是否能够及时告警并定位到完整链路。

本设计建设覆盖整个 Agent 的生产级评测与观测体系，范围包括：

1. Agent 编排与意图识别。
2. 业务工具选择、参数生成、调用保护和结果门禁。
3. 知识文档解析、索引、发布、混合检索、重排、证据和引用。
4. 短期记忆、会话摘要和跨会话长期记忆。
5. Redis Stream、SSE 中继、心跳、重连、重放与取消。
6. 安全、租户隔离、成本、容量、任务积压和发布质量门禁。

评测用于回答“系统做得对不对”，观测用于回答“真实请求发生了什么以及为什么”。二者共用版本、链路和结果语义，但不能混为同一套数据。

## 2. 方案比较

### 2.1 方案一：仅增加日志和单元测试

优点是实现快、依赖少；缺点是无法跨服务还原请求、无法持续比较模型质量、无法形成线上 SLO 和发布门禁。只适合作为开发阶段补充，不满足生产要求。

### 2.2 方案二：在 Agent 服务内部实现评测并直接写 Prometheus

优点是改动集中；缺点是评测任务会与在线流量争抢模型、线程和数据库资源，知识服务与异步 Worker 的链路也难以统一管理，无法独立扩容和限流。

### 2.3 方案三：独立评测控制面与统一 OpenTelemetry 观测面（采用）

新增独立评测服务负责数据集、运行、评分、基线比较和发布门禁；Agent Server 与 Knowledge Service 只提供受控评测入口和业务遥测。所有服务通过 OpenTelemetry SDK 和 Collector 统一采集指标、日志与 Trace，分别落到 Prometheus、Loki 和 Tempo，并由 Grafana 展示，Alertmanager 负责告警路由。

该方案组件较多，但职责边界清晰，可以独立部署、限流和扩容，并支持生产级跨服务追踪、故障定位和质量回归。开发环境可以选择性启动组件，但生产代码和遥测协议保持一致。

## 3. 总体架构

```text
Git 中的脱敏黄金集                 线上脱敏抽样/人工标注
          │                               │
          └──────────► Evaluation Service ◄──────────┐
                         │ 运行、评分、基线、门禁      │
                         ▼                            │
                    Evaluation MySQL                 │
                         │ 大型脱敏产物               │
                         ▼                            │
                       MinIO                          │
                                                     │
桌面端 → Gateway → Agent Server → Knowledge Service ┤
                    │   │   │          │             │
                    │   │   └→ Redis/ES/Milvus       │
                    │   └────→ 业务工具/下游服务      │
                    └────────→ MySQL/RabbitMQ/MinIO   │
                                   │                 │
             OpenTelemetry SDK / 自动与手工埋点       │
                                   ▼                 │
                         OpenTelemetry Collector      │
                         ├─ Prometheus：指标          │
                         ├─ Tempo：Trace              │
                         └─ Loki：结构化日志          │
                                   ▼                 │
                       Grafana + Alertmanager ────────┘
```

评测服务不直接读取生产业务数据库拼装“标准答案”，避免将当前实现误当成正确基线。黄金答案由脱敏夹具、人工标注或可验证的测试数据产生。线上抽样只用于发现问题和生成候选样本，进入正式黄金集前必须人工审核。

## 4. 统一链路和遥测规范

### 4.1 关联标识

每轮请求继续以 `requestId` 作为业务关联标识，以 OpenTelemetry `traceId/spanId` 作为技术链路标识：

- `requestId`：贯穿 HTTP、后台 Agent 任务、Redis Stream、取消和最终持久化。
- `traceId/spanId`：贯穿 Gateway、Agent、Knowledge Service、业务下游、RabbitMQ 和异步 Worker。
- `conversationId`：只用于日志与 Trace 定位，禁止作为 Prometheus 标签。
- `evaluationRunId/evaluationCaseId`：仅评测流量携带，存放于 Trace 属性和评测数据库，不作为高基数指标标签。

HTTP 使用 W3C `traceparent/tracestate` 传播；RabbitMQ 消息头、Outbox 事件和异步任务保存必要的 Trace 上下文。Redis Stream 业务事件仍保持现有协议，不把完整 Trace 上下文暴露给前端，只保留后端诊断需要的关联字段。

### 4.2 Span 层级

一轮问答至少包含以下 Span：

```text
agent.turn
├─ agent.identity.verify
├─ agent.conversation.acquire
├─ agent.context.load
│  ├─ memory.short_term.load
│  ├─ memory.summary.load
│  └─ memory.long_term.recall
├─ agent.intent.plan
├─ agent.model.stream
│  └─ agent.tool.call（每次工具调用一个 Span）
│     ├─ knowledge.retrieve
│     └─ downstream.http
├─ agent.result.gate
├─ agent.turn.finalize
├─ redis_stream.publish
└─ sse.relay / sse.replay
```

Knowledge Service 的文档处理链路独立建立 `knowledge.ingestion` 根 Span，并连接解析、OCR、切片、Embedding、ES 写入、Milvus 写入、发布和清理阶段。摘要和长期记忆任务分别建立独立根 Span，并通过 Span Link 关联原始对话，而不是伪装成仍在同一个长事务中。

### 4.3 统一属性

低基数属性包括：

- `service.name`、`deployment.environment`、`service.version`
- `agent.intent`、`agent.plan_type`、`agent.outcome`
- `model.provider`、`model.name`、`prompt.version`
- `tool.name`、`tool.outcome`、`error.type`
- `knowledge.degradation`、`knowledge.answerable`
- `memory.layer`、`memory.outcome`
- `sse.event_type`、`sse.terminal_state`

用户、租户、会话、文档、请求和任务 ID 只能出现在受访问控制的日志或 Trace 属性中，并按策略哈希或脱敏，不能成为指标标签，防止指标基数失控。

### 4.4 日志规范

所有服务输出 JSON 结构化日志，自动包含 `trace_id`、`span_id`、`request_id`、服务、环境、版本、阶段、结果码和安全错误摘要。禁止记录：

- 用户原始消息、完整模型提示词和完整模型回答。
- 记忆事实正文、知识证据正文和下游敏感 DTO。
- Token、Cookie、内部密钥、身份证号、手机号等认证或个人敏感数据。

需要复盘内容质量时，仅在评测环境保存脱敏夹具；生产抽样内容进入专用受控存储，设置独立权限、留存期和删除机制。

### 4.5 采样策略

- 错误、超时、取消失败、门禁拒绝和安全事件：100% 保留 Trace。
- 评测流量：100% 保留 Trace。
- 普通成功流量：Collector 使用尾部采样，初始比例由环境配置，生产建议从 5%～10% 起步。
- 指标不采样，日志按级别和速率限制处理。

## 5. 评测控制面

### 5.1 独立服务

新增独立 `order-logistics-agent-evaluation-service`，职责包括：

- 管理数据集、样本、标签、评分规则和版本。
- 创建即时、定时、发布前和基线对比评测运行。
- 多实例安全领取任务、执行限流、失败重试和租约恢复。
- 调用 Agent、Knowledge Service 的受控评测入口。
- 执行确定性评分、检索评分、语义评分和安全评分。
- 生成模块得分、失败样本、版本对比和发布门禁结论。

评测 Worker 使用独立线程池、独立模型并发额度和独立服务身份，不能与在线请求共享无限制资源。业务工具评测默认使用沙箱租户和固定夹具；任何具有写操作的工具必须使用模拟下游或执行后可清理的隔离环境。

### 5.2 数据模型

独立数据库 `order_logistics_agent_evaluation` 至少包含：

| 表 | 作用 |
|---|---|
| `eval_dataset` | 数据集名称、模块、版本、状态和适用范围 |
| `eval_case` | 输入、上下文夹具、期望行为、标签和评分器配置 |
| `eval_run` | 一次评测的代码、模型、Prompt、配置和数据集版本 |
| `eval_case_result` | 单样本实际输出、终态、耗时、Token和总分 |
| `eval_metric_result` | Recall、F1、成功率等聚合指标 |
| `eval_assertion_result` | 单条确定性或语义断言结果及安全原因码 |
| `eval_baseline` | 已批准基线运行与允许回退阈值 |
| `eval_gate_result` | 发布门禁结论、失败指标和批准记录 |
| `eval_annotation_task` | 线上候选样本的人工复核任务 |

数据库保存结构化结果和脱敏摘要；大型响应、检索候选、Trace 快照和报告写入 MinIO，数据库只保存对象键和内容哈希。

### 5.3 数据集管理

黄金集按模块拆分并版本化：

- `intent-routing`：意图、计划类型、工具名称和冲突边界。
- `tool-calling`：工具选择、参数、身份注入、失败和结果门禁。
- `knowledge-ingestion`：PDF/OCR/表格/标题/章节/Chunk 期望结果。
- `knowledge-retrieval`：问题与相关 Chunk 的分级标注。
- `knowledge-answer`：答案要点、引用、不可回答和冲突证据。
- `memory-short-term`：完整轮次、Token预算和缓存一致性。
- `memory-summary`：事实保留、覆盖边界和幻觉。
- `memory-long-term`：显式/隐式、事实Key、时间覆盖、删除和召回。
- `sse-resilience`：乱序、断连、重放、取消、超时和唯一终态。
- `security`：越权、Prompt注入、敏感内容和跨租户隔离。

每个样本必须声明 `caseId`、模块、输入、固定上下文、期望结果、评分规则、风险等级和数据版本。禁止直接把未经审核的线上对话自动加入黄金集。

### 5.4 评分器

评分器按可信度排序：

1. **确定性评分器**：精确值、枚举、Schema、权限、终态、事件序号、工具参数和数据库状态。
2. **信息检索评分器**：Precision@K、Recall@K、MRR、nDCG、引用覆盖率。
3. **规则型事实评分器**：工具结果/证据中的金额、状态、时间和条件是否被回答准确引用。
4. **语义评分器**：完整性、相关性、表达质量和摘要事实保留。
5. **LLM Judge**：只评估难以确定性判断的语义维度，必须使用固定量表、结构化输出、Judge版本和抽样人工校准。

业务正确性、安全性和租户隔离不能只依赖 LLM Judge。Judge 自身的输入输出、Token、版本和置信度也必须进入评测记录。

### 5.5 运行模式

- **提交级评测**：不调用真实付费模型的确定性测试与小型固定集。
- **发布前评测**：使用候选代码、模型、Prompt和配置运行完整关键集。
- **夜间评测**：运行完整黄金集、故障注入和成本回归。
- **基线对比**：同一数据集比较候选版本和已批准版本，既看绝对阈值也看回退幅度。
- **线上抽样评审**：只对脱敏样本生成标注任务，不直接改变基线。

## 6. 分模块评测与观测

### 6.1 Agent 编排与意图识别

评测覆盖规则层和模型层：实时业务排除、知识问题、显式记忆、用户画像查询、普通闲聊、模糊问题、多意图问题和对抗问题。分别计算意图 Precision、Recall、Macro-F1、计划类型准确率、工具选择准确率、无需工具时的误调用率以及规则与模型冲突率。

观测记录意图分布、规则命中、模型工具选择、计划类型、上下文构建耗时、模型首 Token 与总耗时、结果门禁结果、最终终态、模型与 Prompt 版本、输入输出 Token 和预估费用。

### 6.2 工具调用

评测覆盖工具名称、JSON Schema 参数、服务端身份注入、同参并发复用、不同工具并行、单轮调用上限、下游业务码、超时、重试、熔断、半开、降级、协议异常以及失败后禁止模型编造。

观测记录每个工具的调用量、成功率、P50/P95/P99、下游错误类型、熔断状态、重试和降级次数、保护器同参复用次数、调用上限拒绝次数、结果校验拒绝原因和工具已完成但最终门禁失败的次数。

### 6.3 知识文档处理与发布

评测覆盖原文提取、OCR、标题与章节层级、表格完整性、Chunk边界、重复块、内容哈希、Embedding维度、ES/Milvus完整写入、草稿隔离、Release原子切换、并发发布、回滚和旧版本清理。

观测记录各阶段任务量、耗时、成功率、重试、死信、租约恢复、Outbox延迟、RabbitMQ积压、每文档页数/单元数/Chunk数、OCR低置信度比例、Embedding调用量与费用、双索引写入差异、发布延迟和清理积压。

### 6.4 知识检索与回答

检索评测分别输出 ES、Milvus、RRF 和重排后的 Recall@K、Precision@K、MRR、nDCG，覆盖同义表达、精确条款、表格条件、跨章节问题、冲突版本、无答案和当前Release过滤。回答评测覆盖可回答判断、事实忠实度、引用正确率、引用完整率、冲突处理和无证据拒答率。

观测记录两路召回耗时与数量、结果重合率、RRF与重排耗时、门槛淘汰数量、降级模式、`answerable`分布、无证据率、Release范围大小、检索期间发布切换重试、最终MySQL校验淘汰数量和知识引用门禁拒绝原因。

### 6.5 短期记忆

评测覆盖完整成功轮次、失败/取消消息排除、Qwen ChatML Token估算、上下文预算、最近原文优先、摘要不挤占近期原文、Redis版本快照、回源和事务提交后预热一致性。

观测记录快照命中率、MySQL回源率、构建耗时、快照字节数、裁剪前后消息与Token、被裁剪轮次、预热队列积压、任务拒绝、版本过期跳过和Redis失败降级。

### 6.6 会话摘要

评测覆盖触发阈值、连续覆盖边界、关键事实保留、无依据新增、与近期原文冲突、任务并发和版本推进。使用确定性事实核对优先，语义评分只补充信息完整性和可读性。

观测记录摘要任务状态、触发原因、覆盖消息范围、输入输出Token、压缩比、模型耗时、重试、租约恢复、版本滞后、协议拒绝和生成后校验拒绝。

### 6.7 长期记忆

评测覆盖显式 SAVE/CLARIFY/NONE、隐式事实抽取、敏感与语义门禁、事实Key规范化、置信度、显式优先、同事实合并、时间范围、当前/历史状态、删除抑制、跨会话召回、ES/Milvus融合、MySQL终检和记忆注入攻击。

观测记录显式解析和语义解析路径、候选数、通过数、保存数、拒绝原因、任务重试与死信、Outbox延迟、索引一致性、召回候选与最终采用数、时间冲突淘汰、删除传播延迟、敏感过滤和跨租户校验失败。

### 6.8 Redis Stream 与 SSE

评测使用可控故障注入模拟网络抖动、连接中断、网关超时、实例重启、Redis短暂不可用、重复重连、并发发送和跨实例取消，验证sequence单调、事件无丢失、客户端去重、断点重放、输入锁定、指数退避、最大重试、心跳、唯一终态、数据库与前端一致性。

观测记录活动连接数、首事件耗时、心跳、断连率、重连尝试/成功/耗尽、重放事件数与耗时、生产与消费sequence差、Redis Stream长度/字节/TTL、重复/跳号、取消类型、取消生效耗时、分布式探针读取和无终态断链。

### 6.9 安全、成本与容量

安全评测覆盖跨租户、伪造身份、知识与记忆Prompt注入、恶意工具参数、敏感日志和删除后残留召回。跨租户泄露、越权工具调用和删除后继续召回属于零容忍门禁。

成本与容量记录单轮模型、Embedding、Rerank、OCR成本，输入输出Token，缓存节省量，最大并发SSE连接，Redis增长速度，ES/Milvus容量，RabbitMQ/Outbox/记忆任务积压和依赖变慢时的级联影响。

## 7. 指标、看板和告警

### 7.1 指标命名

在保留现有指标兼容性的同时，新增指标统一使用业务域前缀：

- `agent.turn.*`、`agent.intent.*`、`agent.model.*`
- `agent.tool.*`、`agent.result_gate.*`
- `agent.memory.short_term.*`、`agent.memory.summary.*`、`agent.memory.long_term.*`
- `knowledge.ingestion.*`、`knowledge.retrieval.*`、`knowledge.release.*`
- `agent.sse.*`、`agent.redis_stream.*`、`agent.cancel.*`
- `evaluation.run.*`、`evaluation.case.*`、`evaluation.gate.*`

指标只使用有限枚举标签，如环境、服务、模块、结果、错误类型、工具名和降级模式。任何可能无限增长的ID不得进入标签。

### 7.2 Grafana 看板

至少建设以下看板：

1. **Agent总览**：请求量、成功率、终态、TTFT、总耗时、Token和费用。
2. **意图与工具**：意图分布、工具准确性代理指标、调用量、熔断、超时和门禁。
3. **知识库**：入库流水线、索引一致性、召回阶段、答案与引用。
4. **记忆**：短期缓存、摘要任务、长期抽取、索引和召回。
5. **SSE可靠性**：连接、心跳、重连、重放、取消和终态完整性。
6. **评测质量**：当前版本对基线、模块得分、失败样本和趋势。
7. **依赖与容量**：MySQL、Redis、RabbitMQ、ES、Milvus、MinIO和模型供应商。

Grafana 必须支持从异常指标跳转到 Tempo Trace，再从 Trace 跳转到 Loki 同一 `trace_id` 日志。

### 7.3 告警分级

- **P0**：跨租户泄露、认证绕过、删除后敏感记忆仍可召回、消息持久化和前端终态发生不可恢复冲突。
- **P1**：Agent错误率或超时率持续超标、Redis Stream大面积重连失败、知识发布不可用、核心依赖熔断持续打开。
- **P2**：评测质量回退、Outbox/任务积压、索引不一致、费用或Token异常增长、缓存命中率显著下降。
- **P3**：单个非核心任务失败、低比例降级和容量趋势预警。

具体阈值不硬编码在业务代码中，由环境配置和告警规则管理。告警包含服务、环境、版本、问题阶段、看板和Runbook链接，不包含用户正文。

## 8. 发布门禁

发布门禁同时检查绝对阈值和相对基线回退：

- 意图 Macro-F1、工具选择和参数准确率。
- 知识 Recall@5、nDCG、可回答准确率、事实忠实度和引用正确率。
- 长期记忆抽取精确率、时间覆盖准确率、删除有效率和跨用户隔离。
- SSE事件丢失、重复终态、重放错误和取消后继续输出必须为零。
- 跨租户、越权、敏感泄露和注入绕过必须为零。
- P95/P99延迟、Token和单轮费用不得超过批准的回退幅度。

门禁失败默认阻止发布。紧急豁免必须记录批准人、理由、有效期和补救任务，不能仅通过修改结果表跳过。

## 9. 一致性与失败处理

- 遥测系统不可用不能阻断聊天主链路；SDK使用有界队列、批量导出和丢弃计数，禁止同步等待Collector。
- 评测服务不可用不影响线上业务，只影响评测和发布门禁。
- Collector、Prometheus、Loki或Tempo不可用时必须产生自身健康指标和告警。
- 评测任务使用租约领取、幂等Case结果Key和可恢复状态，实例宕机后可以继续执行。
- 同一评测运行固定代码、模型、Prompt、Nacos快照、数据集和评分器版本；中途发生版本变化时标记运行无效，不允许与基线比较。
- LLM Judge失败或协议不合法时不能默认为通过，应标记 `UNSCORED` 并根据门禁策略重试或阻止发布。

## 10. 配置与安全边界

生产配置通过Nacos和环境变量管理，至少包括采样率、OTLP端点、评测并发、模型额度、数据留存、告警阈值和门禁标准。密钥只通过Secret注入，不进入Nacos明文、Git、日志和评测结果。

评测服务使用独立账号、独立数据库和最小权限服务凭证。线上抽样默认只保存安全元数据；如需内容评审，必须经过脱敏、授权、访问审计和到期删除。

## 11. 分阶段实施

### 阶段一：遥测基础和统一语义

- 引入OpenTelemetry依赖、Collector和Trace上下文传播。
- 统一结构化日志、指标命名和敏感数据规则。
- 接通Prometheus、Loki、Tempo、Grafana和Alertmanager。
- 建立Agent总览、依赖和SSE基础看板。

### 阶段二：各业务域补齐埋点

- Agent意图、模型、工具和结果门禁。
- Knowledge入库、Release、检索和引用。
- 短期记忆、摘要、长期记忆与索引。
- Redis Stream、重连、重放、取消和统一终态。

### 阶段三：评测控制面

- 新建评测服务、数据库、MinIO产物和Worker。
- 实现数据集、运行、评分、基线和报告API。
- 优先接入确定性评分和检索评分，再接入受控LLM Judge。

### 阶段四：黄金集与故障注入

- 建立各模块脱敏黄金集。
- 建立网络、Redis、RabbitMQ、ES、Milvus、模型和下游故障注入。
- 验证降级、一致性、恢复和安全零容忍场景。

### 阶段五：发布门禁与线上闭环

- 接入CI/CD发布前评测。
- 建立夜间全量评测和线上抽样人工复核。
- 建立基线趋势、成本预算、SLO和分级告警Runbook。

## 12. 验收标准

1. 任意保留的请求都可以从Grafana指标进入Tempo Trace，再定位到相关Loki日志。
2. Trace可以展示Agent、知识服务、异步任务、工具下游和SSE阶段，不泄露用户正文和密钥。
3. 评测运行能够固定并展示代码、模型、Prompt、配置、数据集和评分器版本。
4. 知识、记忆、工具、SSE和安全关键集均能自动运行并产出结构化报告。
5. 候选版本低于绝对阈值或超过允许回退时，发布门禁自动失败。
6. Collector或任一观测后端故障不会阻断正常聊天，并能够观察到遥测丢弃。
7. 跨租户泄露、越权、SSE丢事件、重复终态等零容忍问题能够被测试和告警发现。
8. 本地环境可以选择性启动观测组件，生产部署保持完整架构和相同遥测协议。

## 13. 面试概括

我们把Agent质量评测和运行观测设计成两套相互关联但职责独立的体系：评测侧由独立服务管理脱敏黄金集、运行版本、确定性评分、检索指标、受控语义评分、基线比较和发布门禁，覆盖意图、工具、知识库、分层记忆、SSE韧性与安全；观测侧使用OpenTelemetry统一贯穿Gateway、Agent、Knowledge Service、异步Worker和外部依赖，由Collector将指标、Trace和结构化日志分别写入Prometheus、Tempo和Loki，再通过Grafana关联展示并由Alertmanager分级告警。每轮请求同时保留业务requestId和技术traceId，高基数标识只进入受控日志和Trace，指标只使用有限枚举标签；错误和评测流量全量保留、普通成功流量尾部采样。最终我们把准确率、知识召回与引用、记忆一致性、SSE不丢不重、安全零泄露、延迟和成本共同纳入发布门禁，使系统不仅能够回答，还能持续证明答案正确、链路可靠、故障可定位且版本升级没有质量回退。
