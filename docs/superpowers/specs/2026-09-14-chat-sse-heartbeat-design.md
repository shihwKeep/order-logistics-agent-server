# 聊天 SSE 心跳与空闲断连检测设计

## 1. 目标

为桌面端到 Agent 的聊天 SSE 链路增加生产可用的连接活性检测：服务端在无正文输出期间定期发送轻量心跳，Electron 主进程在长时间收不到任何事件时主动终止失活连接，并沿用现有统一收尾流程保存最终状态。

本阶段只解决连接保活和失活检测，不实现自动重发用户消息、跨连接事件重放或断点续传，避免网络恢复时重复创建消息和重复调用模型。

## 2. 当前链路

桌面端通过 Electron 主进程使用 `POST + Fetch ReadableStream` 请求 Gateway，Gateway 转发到 Agent 的 `/api/v1/chat/stream`。Agent 使用 `SseEmitter` 输出 `session`、`status`、`delta`、`result`、`error` 和 `done` 事件。

当前已经具备用户取消、SSE 发送异常、后端超时和统一数据库收尾，但没有应用层心跳；连接建立后如果中间代理保留了失效连接，客户端的 `reader.read()` 可能长时间等待，也无法区分正常静默与连接失活。

## 3. 方案选择

### 3.1 方案 A：只发送 SSE 注释心跳

服务端定时发送 `: ping` 注释。代理可以看到字节流活动，但现有 Electron 解析器会忽略注释，客户端无法基于协议事件刷新空闲期限，也无法测试心跳顺序。

### 3.2 方案 B：显式 heartbeat 事件与客户端空闲检测

服务端发送标准事件信封，类型为 `heartbeat`，继续携带全局递增的 `sequence` 和 `timestamp`；Electron 验证并消费该事件但不渲染聊天内容，同时把收到任何合法事件都视为连接活跃。该方案沿用现有事件协议、序号、IPC 边界和测试方式。

这是本次采用的方案。

### 3.3 方案 C：完整断点续传与事件重放

服务端持久化或缓存事件日志，客户端携带 `requestId + sequence` 重连并补拉缺失事件。它可以实现真正的断点恢复，但需要重放存储、过期策略、节点间共享和终态查询协议，超出本次保活需求，留到独立阶段设计。

## 4. 后端设计

### 4.1 配置

聊天流配置增加可校验的心跳间隔，并把当前 SSE 总生命周期配置化。默认值保持：

- SSE 总生命周期：30 秒；
- 心跳间隔：10 秒；
- 心跳间隔必须大于零并显著小于总生命周期。

配置由 Agent 的外部配置覆盖，代码提供安全默认值。心跳不会刷新或延长 SSE 总生命周期，业务超时与连接保活仍是两个独立边界。

### 4.2 调度

使用进程级共享的有界调度器执行心跳，不为每个会话创建线程。每条活动聊天流只持有一个可取消的调度句柄。

心跳必须满足以下生命周期规则：

1. `session` 成功发送后才允许发送第一次 `heartbeat`，保证前端先获得 `conversationId` 和 `requestId`；
2. `done`、`error`、用户取消、发送异常、超时和 emitter 完成时取消调度句柄；
3. 心跳发送失败时按现有 `OUTPUT_ERROR` 路径请求停止，由统一收尾器处理数据库状态；
4. 调度任务不得保存用户正文、Token 或工具结果。

### 4.3 事件协议

新增事件：

```json
{
  "type": "heartbeat",
  "sequence": 3,
  "timestamp": "服务端时间",
  "payload": {}
}
```

`heartbeat` 与其他事件共用 `ChatSseSession` 的同步发送方法，因此同一连接内不会与 `delta`、`result` 或终态事件交叉写入；它占用正常的递增序号，但不写入消息表和结果表。

## 5. Electron 客户端设计

### 5.1 协议消费

共享聊天事件类型和 IPC 传输白名单加入 `heartbeat`。渲染进程收到心跳后只完成协议校验和序号去重，不修改消息正文、卡片、创建时间或完成状态。

现有 `ChatAccumulator` 继续对同一条流内重复的 `sequence` 去重。由于每轮请求的序号都会从 1 开始，本阶段不把它描述为跨请求幂等；未来事件重放必须使用 `requestId + sequence`。

### 5.2 空闲检测

Electron 主进程在 SSE 握手成功后启用空闲检测，默认 25 秒内必须收到至少一个完整合法事件。每次成功解析事件后刷新期限。

空闲超时后：

1. 中止 Fetch 控制器并取消流读取；
2. 删除本地活动流句柄；
3. 向渲染进程返回明确的连接空闲超时错误；
4. 不自动重新提交原消息。

连接建立仍沿用现有 10 秒超时。裸 EOF、读取异常、协议错误和空闲超时均属于客户端传输失败；服务端主动发送的 `error` 仍属于协议内终态，两者不能混为同一种事件。

## 6. 错误与恢复语义

- 预期的“未查询到数据”等业务结果继续通过普通回答和 `done` 完成，不使用错误事件；
- 已建立 SSE 后发生的业务异常、模型异常和后端总超时，由服务端发送带安全错误码的 `error`；
- 网络或 Gateway 已切断连接时，服务端无法再把 `error` 送达，客户端通过读取异常、裸 EOF 或空闲超时判断传输失败；
- 所有后端异常继续进入现有统一收尾事务，先保存消息最终状态并释放会话占用，再尝试发送终态；
- 客户端断连后不盲目重试 POST，用户重新加载会话时以 MySQL 历史状态为准。

## 7. Gateway 与反向代理要求

本次不直接修改共享 Gateway 或外部 Nginx 配置，因为 Agent 路由和生产代理配置不在两个目标仓库内统一管理。上线前必须确认：

- Gateway/Nginx 的响应超时大于 Agent SSE 总生命周期；
- 代理空闲读取超时大于心跳间隔；
- SSE 路由不聚合或缓冲响应；
- 任何更外层负载均衡器的空闲超时遵循相同约束。

当前 Gateway 仓库没有发现明确的 Agent SSE 路由超时配置，因此该项必须作为部署配置核对项记录，不能仅凭应用心跳宣称链路已经完整保活。

当前参数与部署约束：

- `agent.chat.stream.timeout=30s`；
- `agent.chat.stream.heartbeat-interval=10s`；
- Electron 主进程空闲检测为 25 秒；
- `/agent/api/v1/chat/stream` 的 Gateway/Nginx read/response timeout 必须大于 30 秒，建议至少 45 秒；
- 代理不得缓冲 `text/event-stream`；
- 心跳只能刷新空闲读取超时，不能绕过网关配置的绝对请求时限。

## 8. 测试

后端自动化测试覆盖：

- `session` 始终早于第一次 `heartbeat`；
- 心跳复用递增序号且不改变现有事件负载；
- `done`、`error`、取消、超时和发送失败后调度停止；
- 多条连接共用调度器但生命周期相互隔离；
- 心跳不延长后端总超时。

Electron 自动化测试覆盖：

- 合法 `heartbeat` 可以通过 IPC 协议校验；
- 心跳不改变聊天正文、结果和完成状态；
- 持续收到心跳时不会触发空闲超时；
- 长时间无事件时取消读取并返回明确错误；
- 收到 `done/error` 后不残留空闲定时器；
- 不会因为断流自动重复提交用户消息。

## 9. 验收标准

1. 模型在两个正文片段之间静默超过一个心跳周期时，客户端仍能收到心跳且页面不新增可见内容；
2. 人为阻断 Gateway 或 Agent 连接后，客户端在空闲期限内结束“正在生成”状态并显示连接异常；
3. 正常完成仍以成功落库后的 `done` 为唯一成功终态；
4. 心跳不会生成聊天消息、知识引用、工具结果、摘要内容或长期记忆；
5. 原有取消、业务错误、模型错误和历史恢复行为保持不变。
